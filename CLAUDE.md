# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Maintenance rule: keep this file current.** Whenever you make a structural change — a new route, a new table, a changed auth/premium rule, a new external integration, a deployment change — update the relevant section of this file in the same session, before ending your turn. This file exists so future sessions don't have to re-read the whole codebase; letting it drift defeats that purpose.

## What this is

MoneyFlow is a personal-finance mobile app for the Uruguayan market (Spanish/es-UY, currency UYU). Users upload bank statement PDFs (OCR-parsed), track spending by category, detect and manage recurring subscriptions, set savings goals, compare supermarket prices across Uruguayan retailers, and get AI-generated savings suggestions. Monetized via a free/premium split (RevenueCat for real purchases — not yet fully wired, see "Premium plan system" below).

Two independent apps in one repo, deployed separately:
- `backend/` — Node/Express REST API, deployed to **Render** (production: `https://money-flow-co41.onrender.com`). Postgres via Supabase.
- `frontend/` — React Native / Expo (SDK 57, RN 0.86.3, React 19.2.3) mobile app.

## Commands

**Backend** (`cd backend`):
- `npm run dev` — start with nodemon (auto-restart)
  - **`EADDRINUSE: :::3000` means a stale server is still holding the port, and the real damage is silent.** On Windows a killed terminal does not necessarily take `node server.js` with it: the orphan keeps listening, nodemon cannot bind, crashes, and sits at *"waiting for file changes"* — while `curl /health` still answers **200**, so the port looks healthy and every `verify-*.js` run against `localhost:3000` silently measures **whatever code that orphan loaded**, which can be hours old. `pkill`/`kill` from the Bash tool do not touch Windows processes. Find and kill it with PowerShell: `Get-NetTCPConnection -LocalPort 3000 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }`, then touch any backend file to wake nodemon. **When a verification result surprises you — passing something you have not implemented, or failing something you just fixed — check the port's owner and its start time before debugging the code.**
- `npm start` — start with `node --dns-result-order=ipv4first server.js` (the IPv4 flag matters — see "Database connection" below)
- `node scripts/verify-security-fixes.js [baseUrl]` — E2E smoke test (registers a disposable user, tests webhook auth, premium gating, hybrid-encryption upload, IDOR, then cleans up everything it created including tables with no FK cascade). Defaults to `http://localhost:3000`; pass a URL to point at Render instead. Requires `DATABASE_URL` to be reachable.
- `node scripts/verify-deploy-goals.js [baseUrl]` — is Render actually serving the code you just pushed? `/health` returns a hardcoded `version: '1.0.0'`, so it cannot tell one deploy from another; this asks the API for something only the new code does (`GET /goals` carrying `feasibility`). It registers a disposable user and **deletes itself through `DELETE /api/account`** rather than touching the database, so a broken account-deletion shows up here too. Defaults to the Render URL.
- `node scripts/verify-goal-linking.js [baseUrl]` — crediting a real bank movement to a goal: does it add once, and can it be undone? Needs a running server (`npm run dev`), defaults to `http://localhost:3000`. Covers the three bugs that endpoint shipped with (double-credit, crediting an income row, no undo), the IDOR case, and what the candidate list does and does not offer.
- `node scripts/categorizer-eval.js` — accuracy of `services/categorizer.js` over 76 hand-labeled cases. Run it before and after touching the rules, and **especially** before replacing the regexes with anything learned: without a baseline there is no way to tell whether a model is better than 15 regexes.
- `node scripts/verify-goal-cost.js` — the spend-in-goal-quotas conversion: does the division come out right, and does it stay silent when it cannot be made (no target date, under two closed months)?
- `node scripts/verify-goal-balance.js [baseUrl]` — asserts that a goal's balance always equals `SUM(goal_deposits)` across every path that moves money, and that the repair migration reconciles a drifted goal without deleting anyone's money. Needs a running server. Ends by printing how many **real** goals are out of balance in each direction — counts only, no names or amounts.
- `node scripts/verify-multicurrency.js` — pesos and dollars in the same account: each movement keeps its own currency and **its own date's** BCU rate, `amount_uyu` is generated by the database and cannot be written by hand, and totals add up in pesos instead of mixing. Hits the real BCU service.
- `node scripts/verify-display-currency.js` — the account the user is looking at is saved server-side and survives a login. Needs a running server.
- `node scripts/verify-account-switch.js [baseUrl]` — asking for one account returns **only** that account, summed in **its own** currency, and empty when it holds nothing. Needs a running server. 11 checks; it pins the contract the screen depends on.
- `node scripts/verify-cfe-qr.js` — parses the QR printed on every Uruguayan e-Ticket / e-Factura, against a **real** one decoded from a photo, and checks that anything which is not a DGI receipt returns `null` instead of throwing.
- `node scripts/verify-receipts.js [baseUrl]` — scanning a receipt: does it load the expense with the QR's exact amount, and does scanning the same ticket twice leave one movement? Also: naming a merchant once leaves it named for **another user** and survives that user deleting their account. 18 checks. Needs a running server. Uses the real QR from a photographed e-Ticket.
- `node scripts/verify-origenes.js [baseUrl]` — where each movement came from: bank statement, scanned receipt, or typed by hand. Needs a running server. 10 checks. The count matters more than it looks: the Movements screen hangs the **delete-imported** button off the bank figure, so a miscount is a person tapping a destructive action believing it takes something else. It also pins that a legacy row with `source` NULL still lands under "by hand" instead of vanishing from the total.
- No lint/typecheck/test-suite scripts exist in this backend. There is no Jest/Mocha config — the verify script above is the only automated check.

**Frontend** (`cd frontend`):
- `npm start` — Expo dev server (Metro). Use `npm start -- --clear` after touching native-module-adjacent code (expo-crypto, expo-file-system) or after changing dependency versions — stale Metro cache is a common source of confusing "module not found" errors.
- `npm run android` / `npm run ios` / `npm run web` — same, targeting a specific platform directly.
- Keep Expo package versions aligned with the SDK: run `npx expo install --check` before adding/upgrading any `expo-*` package, and `npx expo install <pkg>` (not plain `npm install`) to install one at the SDK-compatible version. A mismatch here fails silently until a native module lookup throws at runtime deep in some screen (e.g. `expo-crypto` was previously pinned to `55.0.14` on an SDK 54 project — should have been `~15.0.9` — which crashed with "cannot find native module ExpoCryptoAES" only when the upload screen's encryption path first ran expo-crypto's code).
- **`expo-file-system` is imported from `expo-file-system/legacy` in `src/utils/encryption.js`, deliberately.** As of SDK 57 the main entrypoint exports only the new `File`/`Directory`/`Paths` API and no longer exports `readAsStringAsync`. The old import kept bundling fine and left `FileSystem.readAsStringAsync` as `undefined`, so the upload would only break when a user actually picked a PDF — the exact silent-failure shape this section warns about. The new API has no base64 read (only `arrayBuffer()`), and hand-rolling that conversion inside the encryption path is risk for no gain. If Expo ever drops `legacy`, migrate with a real upload test, not by eye.
- **SDK 54 → 57 upgrade (done via `npx expo install expo@^57` then `npx expo install --fix`)**: `npx expo install --check` reports clean and both `expo export --platform android` and `--platform ios` bundle without errors. When patch drift accumulates (twelve packages had slipped one patch each by the time glass was added), `npx expo install --fix` takes them all — do it on its own, not tangled into a feature change, so a regression has one candidate cause. Every native API the app calls was verified to still exist on its package's declared entrypoint (`getRandomBytesAsync`, the three `SecureStore` calls, `getLocales`, `isDevice`, `LinearGradient`, `openBrowserAsync`, the `Notifications` set, `getDocumentAsync`). `react-native-purchases` stays at 10.0.0 (latest is 10.9.0) — `expo install --fix` does not manage it, it declares no `codegenConfig` for the New Architecture, and its `require` is wrapped in try/catch so an incompatibility degrades to the mock rather than crashing. **Still untested on a real device**: upload encryption end-to-end and secure-store token persistence across restarts. **Push registration is confirmed working** — an iPhone in Expo Go logged `[notifications] Push token registered: ExponentPushToken[…]`, so `routes/pushToken.js` and the bill reminders have a real token to aim at. (Expo Go still warns that `expo-notifications` is limited there and that **Android** remote notifications were dropped from Expo Go in SDK 53; both need a development build to exercise fully.)
- **`node scripts/verify-native-apis.js` after any Expo version change, because bundling proves nothing here.** `expo export` succeeds even when a function has left its entrypoint: the import stays valid and the value is `undefined`, so it does not fail at build time — it fails when a user opens the screen that calls it. That is precisely how `readAsStringAsync` broke the upload on the SDK 54→57 move. The script reads each package's compiled type declarations (these packages cannot be `require`d from plain Node — they are built for the React Native bundler) and checks the **exact file**, since finding the name anywhere in the package proves nothing: the first version of this check matched a deprecation-warnings file and reported a false OK. Add a line when the app starts calling a new native API.
- `react-native-purchases` (RevenueCat) requires a native module not present in Expo Go — expect it to fall back to the mock in `services/purchases.js` unless running a custom dev client / production build.

## Architecture

### Backend request flow

`server.js` wires up: CORS (allowlist, see Security below) → JSON/urlencoded body parsing (15mb limit) → global rate limiter (100 req/15min/IP) → per-route mounting under `/api/*`. Every route file (`routes/*.js`) does `router.use(authMiddleware)` near the top except `routes/webhooks.js` (RevenueCat calls it, no user session exists) — auth is JWT bearer, verified in `middleware/auth.js`, decoding to `req.userId`. There is no session/cookie auth anywhere.

**Authorization model — read this before adding any query.** There is no database-level authorization. Row Level Security is `ENABLE`d on `transactions`, `subscriptions`, and `goals` in `db/schema.sql`, but **no RLS policies are defined for them**, and the backend connects via `DATABASE_URL`'s pooler role, which bypasses RLS entirely (it's not going through Supabase's PostgREST/anon-key layer where RLS would normally apply). RLS is therefore decorative and enforces nothing on this connection. **The only real authorization boundary is `WHERE user_id = $1` (or an equivalent ownership subquery) hand-written in every query.** Every new query that touches a per-user resource must include this filter explicitly — there is no safety net if you forget it.

Premium gating is a second, separate middleware: `middleware/requirePremium.js`, which re-queries `users.plan`/`plan_expires_at` per-request (not cached) and returns `403 {error: 'premium_required'}` if not active premium.

### Data model

Tables in `db/schema.sql` (users, transactions, subscriptions, goals) have proper `REFERENCES users(id) ON DELETE CASCADE`. Tables created ad-hoc in `db/index.js`'s `initSchema()` (`bills`, `goal_deposits`, `budgets`, `shopping_lists`, `shopping_items`, `search_log`, `search_click`) do **not** have FK constraints back to `users` at all — deleting a user leaves orphaned rows in those tables.

**`DELETE /api/account` is the one place that deletes a user**, and its query set in `routes/account.js` is the authoritative one. It runs inside a single transaction because a half-finished delete is worse than none: the user believes they left and their statements are still there. **Adding a table with a `user_id` means adding it to that set** (a table with no `user_id` is the exception — see `cfe_emisores` under Receipts) — the older list in `scripts/verify-security-fixes.js` had already gone stale, missing `search_log` and `search_click`, which is exactly the failure mode. `node scripts/verify-account-deletion.js` seeds a disposable user into all eleven tables, runs the set and exits non-zero if a single row survives. The endpoint re-checks the password with bcrypt even though the JWT is already valid: a stolen token should not be enough for something irreversible. `GET /api/account/export` ships alongside it, because being able to leave without taking your data is not really being able to leave.

`initSchema()` runs on every server boot (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`) — it's the migration mechanism. There is no separate migration tool/history; schema changes are made by editing `initSchema()` (idempotent DDL) or `schema.sql` (initial bootstrap, run manually once in Supabase's SQL editor) and letting the next boot apply it.

`goal_deposits.transaction_id` (nullable) records which bank movement a deposit came from, when it came from one — it is what makes `DELETE /api/goals/link-transaction/:id` able to reverse exactly one credit. Deposits typed by hand leave it NULL.

`shopping_items.list_id` and `goal_deposits.goal_id` are the only "second-hop" ownership cases — a query filtering by `list_id`/`goal_id` alone is not enough; it must also verify that list/goal belongs to `req.userId` (see `routes/shopping.js`'s `DELETE /items/:id` for the correct pattern: `list_id IN (SELECT id FROM shopping_lists WHERE user_id = $2)`).

### Upload pipeline (hybrid encryption + OCR)

This is the most non-obvious subsystem — read fully before touching `routes/upload.js`, `services/uploadKeys.js`, or `frontend/src/utils/encryption.js`.

1. Client (`frontend/src/utils/encryption.js`) generates a random AES-256 key + IV using `expo-crypto.getRandomBytesAsync` (a real CSPRNG) — **not** `crypto-js`'s or `node-forge`'s own random functions, both of which silently fall back to weak entropy (or throw) in bare React Native with no `global.crypto` polyfill.
2. It encrypts the file (AES-256-CBC via `crypto-js`) and separately encrypts the AES key itself with the server's RSA-2048 public key (RSA-OAEP/SHA-256 via `node-forge`), fetched once per session from `GET /api/upload/public-key`.
3. It POSTs `{ encryptedData, encryptedKey, iv, mimeType, filename }` to `POST /api/upload`.
4. Server (`services/uploadKeys.js`) holds the RSA private key (env var `UPLOAD_RSA_PRIVATE_KEY_B64`, base64-encoded PKCS1 PEM) and is the only thing that can recover the AES key (`crypto.privateDecrypt` with OAEP padding). This means a logged/leaked request body alone is not decryptable — a deliberate improvement over the previous scheme, which sent the raw AES key in the same request as the ciphertext (defeating the point of encrypting at all). **Do not revert to sending a raw/hex AES key in the request** — the server explicitly rejects that old payload shape (`{ key, iv }` without `encryptedKey`) with `400 Payload cifrado requerido`.
5. After decryption the route branches on file type. **A CSV never touches pdf-parse**: `parseCSVTransactions()` reads it directly, and that is the path to prefer. Measured against a real Santander statement in both formats — **the CSV yields 16 transactions and the identical PDF yields 0**. pdf-parse did NOT fail on it (2,334 chars extracted cleanly, so the "bad XRef" worry below did not materialise here); the text simply comes out tabulated at ~13 characters per line and none of the three PDF parsers recognises it. Anything else goes through `extractTextFromPDF` and `parseTransactions()`, which tries BROU, Santander and generic in order until one yields >2 matches.
   - **The CSV parser trusts neither the header nor the positions — it verifies a property of the data.** Mapping by header name was the first attempt and it was wrong: Santander's header declares 8 columns (Fecha, Referencia, Concepto, Descripción, Débito, Crédito, Saldos, "") and the data rows carry 7, because they never emit `Descripción`. Everything past position 2 is shifted one place, so "Crédito" landed on the **balance** column and a 1,000-peso fill-up at ANCAP was imported as 43,311 — the account balance. Reported by the user, who knew the real amount. The property that does hold, and can be checked against the file itself: **a running balance changes between consecutive rows by exactly that row's amount.** In the real statement it holds 11/11 and 4/4, unambiguously. The **sign comes from the balance too** — up is a credit, down is a debit — which is sturdier than deciding which of two numeric columns was named "Débito"; before that, the 11 debits and 5 credits were reported inverted. It needs a quote-aware split (RFC 4180) — a plain `split(',')` gives 7 or 8 columns against an 8-column header because the concept fields contain commas and are quoted. Uruguayan banks send **windows-1252**, so reading as utf-8 breaks every accent, including the column names the mapping depends on. The preamble (client, account, currency, branch) and the opening/closing balance rows have the same column count as data rows but do not begin with a date, which is how they are dropped without hard-coding labels.
   - **Never log or return the statement text.** The route used to `console.log` the first 300 and 800 characters and put `extractedTextSample: text.substring(0, 500)` **in the 422 response body**. That is the account holder's name, account number and movements — going to Render's logs and, worse, over the network where any proxy or error tracker on the path keeps it. The whole hybrid RSA+AES design exists so a leaked request body is not decryptable; logging the plaintext beside it cancels the point. Only sizes are logged now. (`rawText` is still stored per-transaction in the user's own row — that is their audit trail, not an exposure.)
6. Parsed transactions are **upserted on `(user_id, external_id)`** and run through `subscriptionDetector.js` to auto-create subscription rows.
   - **The old `ON CONFLICT DO NOTHING` deduped nothing.** The only unique index on `transactions` was the primary key — a fresh UUID per row — so nothing could ever conflict and every re-upload of the same file inserted everything again. `inserted++` was counted even when the statement had skipped, so the number reported back was wrong too.
   - `external_id` is `date|bank reference`, taken from the statement's own reference column (verified unique across all 16 rows of a real file; the parser only uses that column as a key when its values are ≥90% distinct, falling back to the description). **The amount is deliberately NOT part of the key**: re-uploading exists precisely to *fix* a bad import, and if the amount were in the key a corrected figure would land beside the wrong row instead of repairing it. `ON CONFLICT … DO UPDATE` therefore makes a second upload idempotent and self-healing, and `RETURNING (xmax = 0)` separates inserts from updates so the response can say what actually happened. `node scripts/verify-upload-idempotency.js` asserts the whole sequence: 3 new, then 0 new / 3 corrected, then 0 new.
   - The index is **partial** (`WHERE external_id IS NOT NULL`) so manual entries and rows imported before the column existed do not collide. Those older rows are invisible to the upsert, which is why `DELETE /api/transactions/imported` exists — scoped to `source = 'ocr'`, with `?rotas=1` narrowing it to rows with no `external_id`, i.e. exactly a pre-fix import.

### Premium plan system

Two independent signals decide `isPremium`, reconciled client-side in `frontend/src/context/PlanContext.js`:
- **DB-driven**: `users.plan` / `users.plan_expires_at`, set by (a) `POST /api/webhooks/revenuecat` (real purchases, see below) or (b) `POST /api/dev/simulate-premium` (dev-only, see Security).
- **RevenueCat-driven**: `react-native-purchases` SDK's `CustomerInfo`, checked directly on-device. Takes priority over the DB value once loaded (`rcPremium !== null ? rcPremium : dbPremium`).

**Current real-world state: RevenueCat is not actually configured.** `frontend/src/services/purchases.js` has literal placeholder API keys (`RC_API_KEY_IOS = 'REPLACE_WITH_REVENUECAT_IOS_KEY'`) — the SDK init is skipped whenever the key still starts with `REPLACE_WITH`, so `isAvailable()` effectively stays mock-mode in practice until real keys are dropped in. Until then, premium status is driven entirely by the DB path (webhook + dev routes). Don't assume RevenueCat purchases work end-to-end without checking this file first.

Feature flags derived from `isPremium` live in `PlanContext.buildFlags()` — add new gated features there, not ad-hoc checks scattered through screens.

### Savings goals

`routes/goals.js` — CRUD plus deposits (`goal_deposits`; a deposit also writes a `transactions` row carrying `goal_id`) and five derived numbers computed server-side and embedded in `GET /goals`, so the list needs no second request: `projection`, `monthlyQuota`, `streak`, `milestones`, `savingsSurplus`.

- **`savingsSurplus` compares at EQUIVALENT DAY, and returns `null` rather than a number when it cannot compare.** The first version took `AVG(monthly_total)` over the last 6 months and subtracted the current month — a *partial* month against full-month averages — so the figure measured **what day it is**, not saving. Simulated over a user spending exactly the same every month it read "Ahorrás $23.714" on day 1, $16.000 on day 10 and $0 on day 30: zero only on the last day of the month, which is precisely when it is useless. Two further errors in the same query: the partial current month sat **inside its own average** (dragging it down), and `NOW() - INTERVAL '6 months'` lands mid-month so the oldest bucket was truncated too. It now sums the first N days of each of the 6 previous months with N = today's day, excludes the current month from the average, and starts the window at `DATE_TRUNC('month', …)` — the shape of Monzo's "spending vs last month" chart, and the only shape whose answer does not depend on the date.
- It returns `null`, **not `0`**, with fewer than 2 comparable previous months or with **no transactions loaded for this month**. That second case is the normal one here rather than the rare one — statements arrive by manual CSV upload, so `MAX(CASE …)` was `NULL` → `0` → the surplus came out as the entire average, announcing a saving over data that does not exist. Same rule as Upload's hardcoded 72% ring: rather than an invented number, nothing. The UI must therefore read `savingsSurplus?.amount`, not the value itself.
- `node scripts/verify-savings-surplus.js` seeds four disposable users — spends the same as always / spends half / nothing loaded this month / only one month of history — and asserts that the first, third and fourth stay silent while the second is detected to the peso. It calls the helper directly through `module.exports.__testing` because the calculation depends on today's date.
- **Feasibility (`services/goalFeasibility.js`, `feasibility` on `GET /goals`) answers the question the progress bar cannot: "does it fit?"** A goal tracker with no bank access can only draw a percentage — how far along you are, never whether you will arrive. The statement is already loaded here, so the monthly quota can be compared against what actually stays: average monthly income minus average monthly spending over **closed** months. This is YNAB's uncomfortable half — saying *no* is more useful than three optimistic bars — and it is the part a pure goal tracker cannot copy.
  - **The margin is ONE and the goals share it.** Verdicts are computed per goal *and* over the sum of quotas, because a per-goal bar cannot see the case that matters: two goals of $12.090/month each both read `alcanza` against a $20.000 margin and together need $24.180. `veredicto` at the top level is the one that decides; `porMeta[]` explains.
  - **A deposit into a goal is not spending.** `POST /:id/deposits` also writes a `transactions` row as `debit` with `goal_id` set, so counting it would mean saving reduces your measured capacity to save — the app would tell someone who funds their goal every month that they cannot afford to fund it. Both this and `calcSavingsSurplus` filter `goal_id IS NULL`. **Any new query that averages spending must do the same.**
  - **Fixed costs are reported, never subtracted twice.** Subscriptions (normalised: yearly ÷ 12, weekly × 52 ÷ 12) and bills are already inside the spending average; they are shown only so the user knows which part of the spend is cuttable.
  - Same two honesty rules as the rest: only **closed** months (the current partial one would drag the average down), and the average divides by months that actually carry movements, not by the window. Under 2 closed months it returns `status: 'sin_datos'` instead of a verdict — feasibility computed over one month is an anecdote.
  - When it does not fit, the response carries the two concrete ways out rather than only the bad news: `faltantePorMes` and `objetivoPosible` (what target *does* fit inside the deadline). The UI renders both.
  - `node scripts/verify-goal-feasibility.js` seeds five disposable users at a known income/spend and asserts each verdict, including the two-goals-share-one-margin case and the goal-deposit exclusion.
  - `calcMonthlyQuota` lives in this service and `routes/goals.js` imports it — the goal card and the feasibility verdict must not be able to disagree about the quota.
- **A goal's balance is DERIVED from its deposit history (`services/goalBalance.js`).** `goals.current_amount` used to be an independent number written by four paths — create, `PATCH`, deposit, link-transaction — while only two of them wrote a `goal_deposits` row, so the two drifted with nothing noticing. On screen that showed as a goal at 12% with $5.827 saved that simultaneously said *"Hacé tu primer depósito para ver cuándo llegás"*: the ring reads the balance, `calcProjection` reads the deposits, and both were rendering their own version of the truth. It is now a cache of `SUM(goal_deposits.amount)` that nothing writes by hand — every path inserts or deletes its history row and then calls `recalcularSaldo(ejecutor, goalId)`, which takes a client so the link/unlink cases stay inside their `BEGIN`. The column is kept rather than summing on every read because the ring, projection, quota, milestones and feasibility all read it and must see the same number.
  - `PATCH /:id` **no longer accepts `current_amount`** — no client ever sent it, and it was the easiest door to a balance the history could not explain. Money moves through deposits.
  - An opening `current_amount` on `POST /goals` becomes a `Saldo inicial` deposit rather than going straight into the column.
  - `initSchema()` reconciles existing rows, **upwards only**: when the balance exceeds what the history explains it inserts the missing `Saldo anterior` row, because that money is real to the user and deleting it would destroy their data. The opposite case is deliberately left alone — raising a balance to match a leftover row could reverse a `Deshacer` the user actually performed — and `verify-goal-balance.js` reports the count instead.
- **Spending measured in goal quotas (`services/goalCost.js`, `costos` on `GET /goals`) — and deliberately NOT a verdict about waste.** "Restaurantes: $4.200/mes — 0,4 meses de tu Notebook". Whether $4.200 of delivery is waste depends on that person's income, on what they would otherwise do, and on their life; a bank statement cannot answer it, and calling it waste is a moral judgment wearing a statistic's clothes. The conversion judges nothing — it divides two numbers the user already knows, their spend and the quota **they set themselves**, and leaves the decision to them. It also does not mark categories as discretionary: it sorts by amount with no adjectives, because deciding which spending is optional is exactly the judgment the file exists to avoid. Needs a goal with a target date (no date, no quota, no conversion — it returns `sin_meta` rather than inventing one), at least 2 closed months, and it excludes goal deposits like every other spending average here. The reference goal is the one with the nearest deadline, and `calcMonthlyQuota` is passed in so the goal card and this cannot disagree about the quota.
- **Crediting a real bank movement (`services/savingsDetector.js`, `GET /api/goals/candidates`, `POST`/`DELETE /api/goals/link-transaction`).** Typing a number into "Ahorrar" proves nothing moved; the savings transfer is already in the uploaded statement, and this points at it. **The app cannot know whether a transfer went to your own savings account or to a friend — the statement does not say** — so it proposes and the user confirms. A false positive costs one dismissal, not a wrong number on screen; that is what separates it from the matching rules this file records failing (PPMI miner, anchor rule, category lexicon), which changed results silently.
  - **Origin is NOT a filter, and making it one was the first version's mistake.** It required `source = 'ocr'` — "the bank said it, not the user" — which excluded the single clearest case there is: someone enters a movement by hand, labels it `Ahorro`, and the goals screen never mentions it. Reported exactly that way. A category the person chose is not noise, it is a **declaration**, and it outweighs any regex over a bank description, which is only an inference — so `category === 'Ahorro'` is now the highest-scoring reason. Noise is held back by the one-reason floor, not by where the row came from.
  - **A candidate with no reason at all is not offered.** Negative eligibility lets through everything the categoriser failed to recognise, and against real data that is a lot: a $195 purchase described only as "MONTEVIDEO" was being offered as a possible saving with not one line saying why. The card promises to explain every row, so a row with no explanation contradicts it and dirties the ones that do have evidence. Scoring still only orders; this is a floor of one reason, not a vocabulary gate.
  - **Eligibility uses NEGATIVE evidence, which is the only kind measured here.** The categoriser already recognises purchases (Supermercado, Restaurantes, Transporte, Salud, Streaming…); those are excluded, plus anything not from the bank (`source <> 'ocr'`), already credited (`goal_id IS NOT NULL`), an income row, under $100, or older than 90 days. What remains is "we don't know what this is", and a savings transfer is necessarily inside it. **The transfer vocabulary only ORDERS, never filters** — same rule as the search route's "eligibility is matching the required tokens; the score only orders". A round amount is a genuine weak signal (a purchase gives 1.347,20; a transfer a person chose gives 1.000), so it ranks and never gates. Each row ships its `motivos` so the user can judge the suggestion.
  - **`POST /link-transaction` shipped with three bugs and had never been called by anything.** It did not check `tx.goal_id`, so crediting the same movement twice **added the amount twice** with no way back; it accepted a `credit`, which put the salary inside the goal; and its three writes were not atomic. All three fixed — 409 on an already-linked movement, 400 on an income row, one `BEGIN/COMMIT`.
  - **`DELETE /link-transaction/:transactionId` exists because the credit is triggered by a *suggestion*.** Without it a single wrong "yes" left the goal permanently inflated — nothing else in the app lowers `current_amount`. `goal_deposits.transaction_id` (added to `initSchema()`) is what makes the link reversible exactly, instead of guessing which deposit came from that movement by amount and text.
  - **In the UI the undo stays on screen, not in a toast.** The credited row keeps a "Deshacer" button in the card for the rest of the session: if the only way to fix a wrong suggestion lasts three seconds, it does not really exist.
  - Still not surfaced: `milestones` (25/50/75/100%) and `GET /:id/insights` — computed and returned, read by nothing.

### Multi-currency

Uruguayans are paid in pesos and save in dollars, and most people hold a peso account *and* a dollar account; some are paid in dollars. Everything used to sum as if there were one currency, so a US$50 charge counted as 50 pesos.

- **Three columns on `transactions`, and the third is what holds the rule.** `currency` (what the original amount is in), `rate_uyu` (how many pesos one unit of that currency was worth **on that movement's date**), and `amount_uyu` — **a `GENERATED ALWAYS AS (amount * rate_uyu) STORED` column**, not one anybody maintains. That is the same lesson as `goals.current_amount`, which drifted from its history precisely because it was a hand-kept number; here the database refuses to let it desynchronise. Every aggregate reads `amount_uyu`, never `amount`.
- **The rate is frozen at the date of the movement, never today's.** Converting with today's rate makes a dollar saving "grow" when the dollar rises, which is false — you did not save more, the exchange rate moved — and it re-values an old expense every time you look at it. `services/exchangeRate.js` gained `getUsdToUyuRateOn(fecha)`; the BCU SOAP service already accepted a date range (`fetchLatestUsdRate` used it to skip weekends), so this needed nothing new from them. Cached **per date with no expiry**, because a past day's rate never changes.
- **The statement's currency comes from the file, not from a question.** A statement is for one account, and the currency sits in the CSV preamble — the same rows the parser already discards for not starting with a date (`detectarMoneda`). It reads **only the preamble**: a description saying "COMPRA USA" does not make the account a dollar account. It returns `null` rather than guessing, and Upload shows a Detectar / Pesos / Dólares selector for that case, because assuming wrong multiplies or divides every amount by forty. The upload response carries `currency` and `currencyDetected` so the app can say which was used instead of the user discovering it when the totals come out 40× small.
- **In the UI a currency is never implicit.** `formatMoney(n, currency)` renders `US$ 50` against `$50`; in Uruguay the dollar is always written `US$`, never a bare `$`, exactly because they get confused. A USD row also shows its peso equivalent underneath, labelled "al cambio del día" — it is reference, and deliberately *not* what it would be worth today.
- **The accounts are SEPARATE, not merged into one converted total.** A peso statement and a dollar statement are two different accounts, and showing them added together in pesos is not what anyone has in mind when they open their bank. `GET /transactions` and `/summary` take `?currency=UYU|USD`; **with one currency selected they sum native `amount`, not `amount_uyu`** — inside the dollar account everything is already dollars and converting would invent a number nobody asked for. Without the parameter they sum in pesos, which is the only way to put both in one figure. `/summary` returns `currency` and `convertido` so the UI renders the right symbol instead of deducing it. `GET /transactions/accounts` lists the currencies the user actually holds, so the switcher is hidden from someone who only operates in pesos.
- **A full-screen spinner is for the first load only; every later change cross-fades.** Reported as an ugly flicker when switching currency — and it was literally the screen unmounting: `setLoading(true)` on every month or account change swapped the whole thing for a centred `ActivityIndicator` and then rebuilt it. Switching accounts is moving between views, not reloading the app, and it reads either as a transition or as something breaking. A `primeraCarga` ref keeps the spinner for the genuine first load; after that the content dips to 0.45 in 110ms and returns over 230ms — out fast so the stale figures are not studied, in slow so the arrival reads as arrival. The transaction list has the same rule at small scale: its spinner now shows only when there are **no** rows yet, because replacing existing rows with a spinner for 300ms is the same flicker in miniature.
  - **`Promise.allSettled`, not `all`.** With `all`, one rejected fetch skips the fade back and the screen stays at 45% opacity permanently. A partial failure must not leave the view half lit.
- **Switching account must refetch, and the dependency array is where that broke.** Reported as "cuando cambio a dólares no cambian las métricas": `fetchSummary`/`fetchTransactions` had `cuenta` in their `useCallback` deps, so they were rebuilt — but the `useEffect` that *calls* them still listed only `[selectedMonth]`, so nothing ran and the screen kept the other account's numbers while the selector moved. The backend contract was already right (`verify-account-switch.js`, 11 checks); this was purely the screen. Switching also clears the category filter, since categories belong to the account you were looking at and an empty list caused by a forgotten filter reads as "there is nothing here".
- **The account switcher is ALWAYS visible, and hiding it was the mistake.** It used to render only when the user already held both currencies, which made it unreachable: you could not look at your dollar account until you had dollars in it, and nothing told you the view existed. Looking at an empty account is a valid answer — "I have nothing here" — and it is also where you realise you can put something there. The empty state distinguishes *this account is empty* from *you have not loaded anything yet*, because saying "no data" while standing in an empty account whose sibling is full would be a lie.
- **The choice is stored on the user, not the phone** (`users.display_currency`, `PATCH /api/account/preferences`): someone who mostly watches their dollar account wants to find it that way after a reinstall or from another device. It applies on screen immediately and saves in the background — a failed save costs the next startup's default, never the navigation. **`/auth/login` had to return it too**: its `SELECT` did not include the column, so the preference only took effect after an app restart, when `/auth/me` runs.
- **Someone who earns in both currencies has to be able to move between them, and three more things had to give way for that:** the form **defaults to the account being viewed** (looking at the dollar account and tapping "+" almost certainly means a dollar movement; on "Todo" there is no obvious answer, so pesos); saving refetches the account list, otherwise the switcher does not appear until the app is reloaded; and if the saved movement belongs to a *different* account than the one on screen, **the view jumps to that account** — without it the movement saves correctly and vanishes from the filtered list, which reads as "it didn't save". The deposit sheet on a goal names its currency for the same reason: typing "500" into a dollar goal without knowing which one it is a factor-of-forty difference.
- **A goal is denominated in the currency you pick, and it cannot change afterwards.** In Uruguay a house or car goal is in dollars. Deposits are stored in the goal's currency, so changing it later would leave a history saying one thing and a target saying another. Linking a bank movement in a *different* currency converts at that movement's own stored rate and records the original amount in the deposit note.
  - **The quota is shown in the goal's currency and compared in pesos** (`cuota` / `cuotaUyu`). Summing a dollar quota with a peso one gives a number that is neither.
  - **Feasibility and goal-cost convert with TODAY's rate, and that is not an inconsistency.** Recording a past movement uses its own day's rate because it is a fact that already happened. A quota is the opposite: a projection forward. "You need US$500/month" has to be weighed against the pesos you have spare *today*, because today is when you decide whether it fits.

### Receipts: the QR is the authoritative part

Every Uruguayan e-Ticket and e-Factura carries a printed QR pointing at the DGI's verification service, with the fields comma-separated in the query:

```
https://www.efactura.dgi.gub.uy/consultaQR/cfe?215080550011,101,A,424298,1007.00,20260730,nh2847…
                                               RUT          tipo serie número total    fecha  hash
```

- **This beats reading the paper, and by a lot.** Amount and date come out exact — no OCR misplacing a comma, no skewed photo, no washed-out thermal paper. And `RUT+tipo+serie+número` identifies the document uniquely nationwide, which is precisely the key needed to not load the same purchase twice (`services/cfeQr.js` returns it as `externalId`, same shape as the statement's). Verified against a real ticket: all six fields match the print, including the `Cód. de Seguridad` shown on paper being the hash's prefix.
- **`POST /api/receipts/qr` turns a scan into a movement, and is idempotent by construction.** It takes the decoded QR **text**, never an image. `source = 'receipt'` (so `DELETE /transactions/imported`, scoped to `'ocr'`, never touches them) and `external_id = cfe|RUT|tipo|serie|número`, which rides the existing partial unique index — scanning the same ticket twice, or two people in the same house scanning it, updates instead of duplicating. **Not premium-gated**, unlike `/upload`; worth a deliberate decision rather than drifting into one.
  - **The QR carries no currency.** The paper prints `Moneda: UYU` but the code does not, so a dollar receipt would land as pesos if it were assumed silently. The endpoint takes an optional `currency` and reports `monedaAsumida: true` when it had to fall back, so the app can say so instead of the user finding out from a total 40× off.
  - **The merchant's NAME is not in the QR either — only the RUT — so there is a shared registry (`cfe_emisores`).** Without it every scan lands as *"Comprobante 215080550011"*, which is the RUT of the issuer: correct, unique, and unreadable. The table is **global and has no `user_id`**, because a RUT is the same company for everyone — whoever types "Unitex" once has named it for every user of the app, including the next person who scans a ticket from that shop. The endpoint looks the name up, learns it when one is supplied (the user, who is holding the ticket, wins over what is stored), and returns `emisorNombre` / `emisorConocido` so the scanner asks **once per merchant** instead of every scan or never.
    - **It is deliberately NOT in `DELETE /api/account`'s delete set**, which is the one exception to the rule above. It holds no personal data — a RUT and a trade name are public — and deleting a user's contributions would make the app forget a shop for everybody because one person left.
    - **A name can be CORRECTED from the scanner, not only supplied when missing.** Nobody validates this table, so whatever the first person types stands for everyone; if the input only appeared when the name was empty, the sole way to fix a wrong one would be editing the database by hand. That is not hypothetical — see the next point. The result card shows *"No es <nombre> · corregir"* and the correction re-posts the same QR, which also renames the movement (the upsert rewrites `description`).
    - **A verification script poisoned this table in production, and the lesson is bigger than the table.** `verify-receipts.js` sent a `description` alongside the **real** RUT of the sample ticket: it named it `Unitex`, then the credit-note case — same RUT, different type and number — overwrote it with `Unitex devolución`, a test caption. `backend/.env` points at the **same Supabase database Render uses**, so "running it against localhost" wrote to production; the disposable user is deleted at the end, but the registry deliberately survives account deletion, so the junk name reached a real person scanning a real ticket — their own purchase labelled as another shop's refund. (The shop is **Vinitex**/CONAPLUS; `Unitex` was also me misreading the logo.) Three fixes: the script never sends a name with a real RUT and uses invented ones for registry cases, it now **asserts the real RUT's row is unchanged** after the run, and `initSchema()` carries a repair narrow enough to lose to a human — it only rewrites the row while it still holds one of those two exact strings. **Any script writing a table that has no `user_id` is writing shared, permanent state: use synthetic keys and assert you left the real ones alone.**
    - Naming a merchant **re-posts the same QR**, which is safe only because the endpoint is idempotent; the write is `ON CONFLICT (rut) DO UPDATE` and wrapped in a swallowed `.catch()`, since a failing registry must never take the movement down with it.
- **`/api/upload` rejects images before decrypting, and says something true.** It accepted `image/jpeg|png|webp` and the picker offers `image/*`, then handed the photo to `pdf-parse` — so choosing a receipt photo produced *"no se pudo leer el PDF"*. Another advertised capability that did not exist, like the "con IA avanzada" copy. The check sits **before** the RSA decrypt, since `mimeType` comes from the request rather than the content and there is no reason to spend a decryption on something being rejected.
- **`components/ReceiptScanner.js` scans live, and the entry point is on Upload, above the file picker.** Not alphabetical order: the QR gives the exact amount off the document, while a statement has to be downloaded from the bank and remembered — it is the path with both less friction and more accuracy, so it goes first. A local `includes('efactura.dgi.gub.uy')` check answers "that is not the receipt's QR" instantly instead of round-tripping. **A `yaLeido` ref is not optional**: a QR in frame fires `onBarcodeScanned` many times a second, and without it one ticket would fire dozens of requests. A failed POST resets it so the user can retry without closing the camera.
  - **`NSCameraUsageDescription` said "Para fotografiar estados de cuenta"** — no longer what the camera does, and that string is what Apple reads at review. It and the `expo-camera` plugin's `cameraPermission` now say what happens: the QR is scanned, no photo is stored or sent, only the code's text leaves the phone. Android gained `CAMERA` in `app.json`.
- **What the QR does NOT carry**: line items, payment method, the IVA breakdown. Vision is still needed for those — but with the QR's total as an anchor, so a misread is *detected* rather than stored.
- **The date in the QR comes in more than one format, and assuming one broke a real scan.** DGI documents `aaaammdd` and Unitex prints it that way; another receipt — same service, same query shape — printed `30/07/2026`. The parser demanded eight digits, returned `null`, and the app told the user *"ese QR no es un comprobante"* about a perfectly valid one. Worse, `verify-cfe-qr.js` **asserted that `30-07-2026` was garbage**: the test encoded the same wrong assumption as the code, so the suite was green over a bug. `fechaISO` now takes `aaaammdd`, `dd/mm/aaaa` and ISO, with slashes or dashes.
  - **The day goes first, and the month is validated rather than reinterpreted.** Uruguay writes `dd/mm`, the same ticket printing `29/06/2028` as its expiry. Reading `05/07` as May would file the expense in another month with nothing signalling it, so a month outside 1..12 is rejected, and the date must survive an ISO round-trip — otherwise a 31 February would enter as 3 March.
- **CFE types 102 and 112 are credit notes: money coming back.** Filing them as `debit` inverts the sign of the movement, so `TIPOS` maps each type to its sign.
- **`cfeQr.js` decodes no images, deliberately.** The QR is scanned on the phone with the native scanner — better than any JS library, and it can tell the user to re-frame while the camera is still open. The server only ever sees the decoded string, so **Render needs no OpenCV**, which would not fit in 512 MB anyway.
- **Reading the QR off a saved photo is a dead end, and that is measured, not assumed.** Of four real receipt photos, exactly one decoded — the one deliberately framed on the QR. In another the QR ran past the bottom edge of the frame (it starts at y≈1742 and is ~375px tall in a 2048px-tall photo, so the bottom-left finder pattern simply is not in the image; no decoder can recover that). People do not frame for a code they do not know is being read, which is the whole argument for scanning live instead of picking from the gallery.
- **jsQR and ZXing-JS both failed on the receipt that OpenCV read on the first try.** Twenty-four preprocessing variants — crops, upscales, global and adaptive thresholds, median denoise, quiet-zone padding — and none of them decoded. OpenCV's `QRCodeDetector` got it from the **whole image with a plain median blur**: all that cropping was making it worse. Worth remembering before building an elaborate preprocessing pipeline: try the strong detector on the raw frame first.

### Categorisation

`services/categorizer.js` is **the only categoriser**, and it is 15 ordered regexes — first match wins, everything else lands in `Otros`. There is no AI in this path (see the copy rule in the design section; the app claimed there was).

- **There used to be two, with different output vocabularies, and that is the bug to never repeat.** `routes/transactions.js` carried its own 9-rule copy, so the same merchant landed in different categories depending on which door it came through: a PedidosYa typed by hand became `Comida` and the same PedidosYa imported from a statement became `Restaurantes` — two slices of the same pie. Salary was `Ingreso` on one side and `Salario` on the other. The route's copy was also written without accents, so `/medica/` never matched "Médica". `subscriptionDetector.js` was a third producer of `Comida`. **Nobody had noticed because `theme.js` had a colour for all four names**, which made the duplication look tidy on screen. `initSchema()` carries a one-time repair for the rows already stored; `Ingreso` is re-decided from the description rather than renamed blindly, because the old rule was `/salario|sueldo|pago|deposito/` and `pago` is broad enough to have swept in things that are not income at all.
- **The order is load-bearing, and one case depends on it.** `ANCAP SUPERGAS` is the household gas bottle and is caught by the utilities rule's `gas` → `Servicios`; `ANCAP LAGOMAR` falls through to the fuel rule → `Transporte`. One rule, both answers right. ANCAP used to sit *inside* the utilities rule, so every tank of fuel counted as a utility bill.
- **Measuring found four dead rules that had never matched anything**: `osse` (the utility is OSE, one s — the water bill only registered when the text said "saneamiento"), `cut[cs]a` (CUTCSA has both C and S, so Montevideo's main bus company never matched), no `farmashop` at all (the country's largest pharmacy chain), and `pedidosya` only unspaced while the bank also writes "PEDIDOS YA". A bare `agua` was the opposite problem — too broad, it swallowed any bottled-water purchase into `Servicios`. Baseline 92.9% → 100% on the suite.
- **The 100% is over cases I hand-wrote from merchant knowledge, not from real statements**, and the file says so. A bank writes `COMPRA 1234 DISCO POCITOS 12/09`, not `Disco`. Treat it as a regression net, not as a production accuracy estimate. The real labels are the corrections users make through `PATCH /api/transactions/:id` — the same "collect it before anything consumes it" situation as `search_log`.
- **If this is ever replaced by a trained model, `categorizer-eval.js` is the comparison that decides.** On-device inference is the shape that fits (the phone has far more than Render's 0.1 CPU, and the description never leaves the device), but note Expo Go loads no native modules — ONNX/TFLite/ExecuTorch all need a dev build. For short-text classification a char-n-gram linear model exported as a few KB of JSON weights runs in plain JS on both server and phone and needs none of that.

### External integrations

- **Supabase**: used purely as managed Postgres (via `pg.Pool` + `DATABASE_URL`, pooler mode, port 6543). Not using Supabase Auth, Storage, or the JS client — `SUPABASE_URL`/`SUPABASE_ANON_KEY` in `.env` are currently unused by the backend code.
- **RevenueCat**: webhook (`routes/webhooks.js`) + client SDK (see above, not yet live).
- **Anthropic API** (`routes/suggestions.js`): `claude-haiku-4-5-20251001`, premium-only, analyzes 3 months of spending + subscriptions + goals, asked to return strict JSON. `formatSpendingForClaude` builds the prompt context from the user's own data only. **The model says what to do; the server supplies every number.** The prompt used to ask for `potentialSaving: 1500` and `monthlySavingPotential: 3000`, and the screen rendered the total in a green `Card variant="best"` **and multiplied it by 12 as "al año"** — a figure invented by a language model, annualised, sitting beside a margin computed from six months of closed statements, with nothing telling the user which was which. Same rule as Upload's hardcoded 72% ring, applied to money. How much someone would save by spending less on delivery is **not computable** — it depends on what they do next. What is a fact is what they spend there today, and what a detected subscription costs. So the model now returns `category` and `subscription` (exact name) and no amounts; the route attaches `gastoMensual` from its own closed-month average and `ahorroSuscripcion` from the subscriptions table (monthly-normalised), and the only headline total is `ahorroVerificable` — the sum of the subscriptions it actually proposed cancelling. If it names a subscription that does not exist, that field stays null. The user's **name was also removed from the prompt**: it added nothing to the analysis and was personal data travelling to a third party.
- **Grocery/retail scraper** (`services/scraper.js`, used by `routes/prices.js` and `routes/shopping.js`): scrapes Uruguayan retailers (Disco/Devoto/Géant via one mechanism, Tienda Inglesa via HTML scraping, El Dorado/Tata via their VTEX/Faststore JSON APIs) for price comparison across categories: `supermercado`, `farmacia`, `belleza`, `ropa`, `hogar` (home/electronics).
  - **Run `node scripts/scraper-health.js` before blaming the matching algorithm for an empty result.** A store whose HTML changed returns `[]`, `Promise.allSettled` drops it, and nothing distinguishes "no stock" from "broken parser" — this is how Farmashop sat broken (its Magento markup lost the bare `product-item` class) while "ibuprofeno returns nothing" got written off as a stock gap. The script canaries every store with a term it certainly stocks and exits non-zero, so it can hang off a cron.
  - **The cache has two levels, and the second one is Postgres — not disk (`services/persistentCache.js`).** Render's free tier gives a service an **ephemeral filesystem** (wiped on every deploy, restart *and* spin-down) and **spins the service down after 15 minutes of inactivity**, so for a low-traffic app almost every first search of the day hit a fully cold scrape: the in-memory `Map` had died with the previous process. Render's own docs point at Postgres for this, and there is already one. L1 stays the `Map` (instant); L2 is the `kv_cache` table, read only on an L1 miss and promoted back into L1. Writes are fire-and-forget — the user already has their results. **The cache must never break the app**: every function there fails silently and disables itself on the first error, so a paused Supabase, a missing SSL mode, or the mocked `db` in the eval scripts all degrade to the old in-memory behaviour instead of throwing. `services/categoryMap.js` persists through the same table for the same reason — its `.category-map.json` is a development convenience that production never sees. `limpiar()` runs once at boot from `server.js`; without it the table grows a row per search term per store forever.
  - **Caching is fresh-30min / stale-2h with single-flight coalescing.** Stale entries are served instantly while refreshing in the background (a cold scrape is 5-12s). Concurrent callers for the same key share one scrape — without that, 4 simultaneous requests for one query fired 40 HTTP requests instead of 10. TTLs are env-tunable via `SCRAPER_FRESH_MS`/`SCRAPER_STALE_MS`, which is also how you test the stale path without waiting 30 minutes.
  - **All fetches go through `fetchWithRetry`** (retries network errors and 429/5xx only, honours `Retry-After`) **and a per-host concurrency cap of 3.** A 10-item shopping list otherwise bursts at the same six hosts; an IP ban breaks the entire app. If you add a store with its own `scrape` function, route it through `fetchWithRetry` too rather than calling `axios.get` directly. `routes/shopping.js`'s `/compare/start` + `/compare/status/:jobId` is an async job pattern (in-memory `jobs` Map, not persisted — job state is lost on server restart) to avoid blocking on slow scrapes; `/compare` (no `/start`) is the older synchronous version kept for backward compat.
  - **Do not add MercadoLibre as a data source.** Investigated this directly: their public search API (`/sites/{id}/search`, `/products/search`) now rejects every request with `403 PA_UNAUTHORIZED_RESULT_FROM_POLICIES` regardless of auth — a self-serve Developer app's OAuth scopes are all seller-account-management permissions (`urn:global:admin:*`, `urn:ml:*:publish-sync`), none grant general catalog search. Their HTML search pages (`listado.mercadolibre.com.uy/...`) also redirect to an anti-bot `/gz/account-verification` challenge even from a real residential IP with a browser User-Agent. Both paths are dead ends without a formal partnership (not a self-serve integration).
  - **`hogar` category needed zero new scraper code** for the grocery-chain side: Tata, El Dorado, Disco, Géant, and Devoto are unified multi-category catalogs (verified live — searching "heladera"/"televisor" through the existing grocery-search code path returns real appliance/electronics results with correct prices) — adding the category was just tagging these stores with `"hogar"` in `SCRAPE_STORES` plus a frontend filter chip. If adding another general-merchandise store in the future, check whether an existing "supermercado" entry's search endpoint already covers it before writing a new scraper.
  - **Dedicated electronics retailers were added too**: ZonaTecno (Fenicio platform, own theme — don't reuse `parseFenicio` unchanged, its price sits in `.precio.venta .monto` specifically to skip a nested conditional-discount price), and NNET/Digital Outlet/TopTecnoUY (identical white-label platform by "Sublime Solutions" — one parser, `parseSublime`, serves all three via `/productos/?buscar=`), and Thot Computación (standard WooCommerce, `parseWooCommerce`, `/?s=&post_type=product`). All five price in **USD**, unlike every other store (UYU) — see next point.
  - **Currency normalization is per-PRODUCT, not per-store — don't regress this to a store-level flag.** Originally implemented as `store.currency === "USD"` gating conversion for a whole store, but that broke on live testing: Disco/Géant/Devoto/Tienda Inglesa have a **mixed-currency catalog** — groceries carry a peso marker (Cencosud: `<span class="mon">$</span>`; Tienda Inglesa: `CurrencySymbol: "$"`) while electronics/appliances in that same search-results page carry a dollar marker (`U$S`), confirmed live (e.g. a $559 Disco TV sitting next to $89-peso milk in the same listing). Each parser now sets `currency: "USD"` on the individual result object when it detects a USD marker (`parseCencosud`/`scrapeTiendaInglesa` check per-product; `parseZonaTecno`/`parseSublime`/`parseWooCommerce` always set it since those 5 stores are 100% USD). `convertResultsToUyu()` in `scrapeStore()` filters for `item.currency === "USD"` and converts only those via `services/exchangeRate.js` (official BCU rate), moving the original into `originalPrice`. This means `price` is **always UYU-comparable** everywhere downstream (routes' sorting/summing/min-max-avg logic needed zero changes) — never gate this on `store.currency` again, and never add a new store/parser that emits a raw non-UYU `price` without setting `currency: "USD"` on that exact item. `exchangeRate.js` caches the BCU rate for 4h and falls back to the last known-good rate if the BCU call fails (in which case USD items are dropped from results rather than shown unconverted — see `convertResultsToUyu`). `routes/shopping.js`'s per-store item breakdown (`storeMap[storeId].items`, distinct from the top-level `cheapest`/`options` fields) now also carries `currency`/`originalPrice` when set (fixed — used to drop them).
  - A separate, now-fixed bug in `parseSublime` (NNET/Digital Outlet/TopTecnoUY): their price is split across two spans (`.pprecio` integer + `.pdeci` decimal), and `.pprecio` itself uses a dot as a thousands separator past 4 digits (`"1.999"` = 1999) — naively concatenating `"${entero}.${decimales}"` without stripping that dot first turns `$1999` into `1.999` (parseFloat truncates at the second decimal point). Strip dots from the integer part before concatenating, always.
  - **Non-UTF-8 encodings**: NNET/Digital Outlet serve `windows-1252` and TopTecnoUY serves `iso-8859-1` (not UTF-8) — `scrapeStore()` fetches as `arraybuffer` and decodes with `TextDecoder` using the response's actual declared charset (defaulting to utf-8) before handing text to cheerio/JSON.parse. Don't revert this to axios's default string decoding — it silently mangles accented characters (´é´ → ´�´) for these stores specifically.
- **BCU (Banco Central del Uruguay)** (`services/exchangeRate.js`): official USD→UYU exchange rate, SOAP web service (no API key, no REST/JSON alternative exists). Used only to normalize the USD-denominated electronics stores' prices into UYU — see the scraper notes above.
- **Search relevance matching** — `services/productMatcher.js` holds every shared primitive (normalize, tokenize, SYNONYMS, `isAccessoryFor`, `hasAllModelTokens`, `dedupeResults`, `filterPriceOutliers`), used by both `routes/shopping.js` and `routes/prices.js`. **Put new matching logic there, not in a route** — these used to be two independent copies and every relevance bug had to be fixed twice. What deliberately stays per-route is the *ranking policy*: shopping.js scores 0-1 and keeps the single best match per store; prices.js scores additively (keyword hits + exact-phrase bonus + "main noun" rule) and returns a ranked browsable list. Key invariants, each found by a real failing search:
  - **Digit-bearing query tokens are mandatory and must match as a whole word** (`\bTOKEN\b`). Covers generation numbers ("Switch **2**") and alphanumeric model/spec codes ("S24", "i5" vs "i7"). They also always survive the short-token filter even at length 1. Dropping the "2" silently degraded "Nintendo Switch 2" into "Nintendo Switch"; substring matching let a bare "2" match inside "32GB"/"2024".
  - **Query tokens match by word-PREFIX, never by substring (`matchesToken`).** `.includes()` let "ipad" match inside "d-i-s-**ipad**-or", and that one false hit cascaded: it counted as a keyword, then triggered the exact-phrase bonus (+10) and the main-noun bonus (+5), putting a CPU cooler at rank 1 for "ipad". Requiring a whole word (`\bipad\b`) is wrong too — prefix matching is load-bearing for Spanish morphology ("panal"→"panales", "leche"→"leches"). The rule that works: **Spanish extends words at the END, never at the beginning**, so a match must start at a word boundary and whatever remains must be an inflectional suffix (`INFLECTION_SUFFIXES`: '', s, es, as, os, a, o). That kills `sal|sa`, `pan|talon`, `mesa|da`, `eu|ropa` while keeping `panal|es`. Use `matchesToken`/`phraseInProduct` for any new token comparison — never raw `.includes()`.
  - **"Sin X" — the product advertises the ABSENCE of what you searched** (`isNegatedMention`): "Pulpa de Tomate SIN AZÚCAR" matched a search for "azúcar". But it must NOT always be excluded — searching "lactosa" or "gluten", what people want *is* the "sin lactosa" product, since nobody buys the ingredient itself. Resolved without a word list: if the term appears affirmed anywhere in the name, it isn't a negation; and `routes/prices.js` only drops negated items when affirmed ones survive, so a query where nothing affirms the term keeps them.
  - **Store-search trust fallback, single-token queries only.** When every filter leaves zero results but the stores *did* return products, they know something the matcher doesn't: "ibuprofeno" returned 0 while the raw scrape had 36 items (Perifar, Actron, Ibupirac) — pharmacy search engines map generics to brand names, and generic/brand share no tokens, so a synonym list would have to enumerate the whole vademécum. Entries come in at `_score: -500` and still pass the accessory/modifier/negation filters. **Restricted to one-token queries deliberately**: with several tokens the store degrades to OR-matching, and "xbox series x" came back with a "Vino Tannat 90 POINTS SERIES", an asadera and a NERF gun, all hooked on "series". There, zero is the right answer.
  - **`isModifierMention` is applied in BOTH routes and has no safety net in `prices.js`.** It lived in productMatcher but only `shopping.js` ever called it, so "leche 3 litros" returned "Helado 3 L Dulce De Leche". Unlike the accessory filter, it does not fall back to showing the rejected items: verified live that no chain stocks 3 L milk, and an ice cream tells the user nothing about milk prices, whereas an accessory at least signals "the console isn't stocked". Zero is the honest answer for a real stock gap.
  - **Accessory suppression is two-layered**: `ACCESSORY_WORDS` (funda, pack, volante, control, juego, memoria, webcam…) plus a grammar rule for "X **para** \<lo buscado\>" / "compatible con \<lo buscado\>" where the searched product appears only *after* the connector. The grammar rule exists because the word list needed reactive extension four times; it catches "Cámara para Nintendo Switch 2" without anticipating "cámara", while correctly leaving "Notebook para estudiantes" alone when searching "notebook". Accessories repeat the base product's full name for SEO, so without this they tie on relevance and win the cheapest-price tiebreak (a $59 Joy-Con pack beat the $879 console).
  - **Unit normalization must cover the abbreviation, not just the spelled-out form.** `2 litros`/`2 L`/`2Lt` all fold to `2l`, same for ml/kg/g. The original regexes only handled the written forms (`lts?` requires "lt", never matched a bare "L"), so a query normalized to "2l" could never match a product labeled "2 L".
  - **`filterPriceOutliers` drops broken placeholder listings** (a bare "Microondas" at $239 next to real ones at $3,400+): under 15% of the query's median, or under 50% when the name adds no brand/model beyond the query itself. This guards the headline "Carrito óptimo" total, which is built from the cheapest match per item.
  - **Unit pricing (`parseQuantity`/`withUnitPrices`/`compareByValue`) decides which offer wins, not absolute price.** Comparing pack sizes by absolute price is the classic "pack size chaos" failure: a 250 ml milk at $44 beat a 1 L carton at $45 ($176/L vs $45/L), and since the "Carrito óptimo" total is built from the cheapest match per item, the headline number recommended the worst value. `parseQuantity` handles the multipack forms stores actually write ("6 x 330 ml", "16Un X30Mt", "12unx30mtrs", "4 un. 30 m", "x 100", "10 Comp."); when adding a new form, extend it there rather than at a call site. Coverage runs 94-99% on supermercado/farmacia/belleza and near zero on ropa/hogar, which is correct — a TV has no unit price.
  - **Ranking is BM25 + domain rules, not one or the other.** BM25 supplies IDF (a rare word like "anticaspa" outweighs a common "shampoo" with no hand-tuning) and term saturation; the exact-phrase bonus, main-noun rule and accessory penalty stay layered on top because they encode retail-specific knowledge BM25 can't infer. Don't replace the domain rules with "just BM25".
  - **Typo tolerance is a fallback, never a first-class matcher**: it runs only when exact matching found too little, scores strictly below exact matches, skips tokens under 5 chars, and never applies to tokens containing digits (confusing "i5" with "i7" is worse than finding nothing). It also must respect the accessory rule — the first version resurrected "Juego para Xbox Series X" for "xbox series x", a query where no store stocks the console.
  - **Entity resolution (`groupProducts`) runs after ranking, and is deliberately conservative.** `/api/prices/search` returns `groups` (one canonical product with its per-store `offers`) alongside the flat `items`; the search screen renders `groups`. Pipeline: block by normalized quantity → IDF-weighted Jaccard → union-find. **A wrong merge is worse than no merge** — it would show "$45 at Disco, $12 at Tata" for two different products — so three hard guards come before the similarity score: quantity must match, mutually-exclusive variants never merge (`VARIANT_GROUPS`: entera/descremada, zero/light, con/sin lactosa…), and two listings from the same store never merge. The 0.72 threshold was calibrated against live data, not picked: at 0.5 it merges Calcar with Conaprole and the regular line with the Ultra line; at 0.7+ every non-exact merge is a real word-order variation. If you loosen it, re-audit what it merges rather than trusting the count. IDF weighting is load-bearing — plain Jaccard rates two different brands of milk as near-identical because they share every generic word.
  - Validated with `scripts/relevance-battery.js` (50 queries over live data across every category).
  - **Both routes are measured, and they need separate harnesses.** `scripts/precision-eval.js` exercises `/api/prices/search`; `scripts/precision-eval-cart.js` exercises the cart comparator through `routes/shopping.js`'s exported `__testing.scrapeItem`. They share the same case file. The cart route was missing four guards the search route had — the main-noun rule (so "Poroto Cololo MANTECA Lata" scored 1.00 for "manteca", identical to real butter), `isNegatedMention`, the store-search fallback, and a hard filter on modifier mentions. **Run both** — for most of this project only the search one existed, and the cart's `RELEVANCE_THRESHOLD = 0.5` ("half the query tokens is enough") silently let a two-word query match on one word: "apple pencil" returned apple cider vinegar, Green Apple vodka and Jack Daniel's Apple, and since the comparator keeps the cheapest match per store, the headline "MEJOR PRECIO" was a $30 incense stick standing in for a $4,909 stylus — the number that feeds the "Carrito óptimo" total. The cart harness reports an extra metric for exactly this: **MÁS BARATO OK**, whether the cheapest pick is itself a correct product.
  - **Labeled cases only find what someone thought to assert — `scripts/audit-disagreement.js` looks for the rest.** Every important bug in this project was found by a human searching manually, not by the battery. This audit flags suspicious results *without knowing the right answer*, over queries deliberately outside the case file. Its strongest signal: the two routes are independent rankings over identical data, so when the search's top result and the cart's cheapest are different products, one of them is usually wrong. It also flags a cheapest far below the set's median, poor token overlap on the top hit, and extreme price spread. Expect roughly half false positives (two coffees of different brands look "different" to the overlap metric) — findings are suspicions to review by hand, and that is still cheaper than waiting for a user to hit them. It found the fridge-organizer, the poroto-manteca and the Tang-powder bugs below.
  - **The stores' own taxonomy is available and worth capturing (`markOffCategoryItems`).** Products from different categories that share a noun — "Agua Lavandina" (bleach) vs mineral water, "Aceite 15W40" vs cooking oil — cannot be told apart by any rule about the *name*: they pass the accessory, modifier and main-noun rules identically. El Dorado's VTEX API returns the real category (`/Limpieza/Limpieza Hogar/Desinfectantes/` vs `/Bebidas/…/Aguas y Aguas Saborizadas/`) and the scraper now keeps it; Tata returns only numeric ids and no other store returns anything. It generalizes to stores without taxonomy by propagating the *vocabulary* rather than the category: words appearing only in the minority branch become an off-category signal for any store, learned per query instead of hand-listed. **Measured neutral on the suite** (99.9% / 99.3% / 100% before and after) — it is kept because it captures real data that was being discarded, is verified harmless, and is the substrate for the real fix, not because it improved a number. **What it does not fix:** El Dorado's search for "agua" returns only drinking water, so there is no minority branch to learn "lavandina" from. Closing that needs a targeted lookup of the *winning candidate* by name against the categorized store's API — one extra request per query, which puts a network dependency inside ranking and should be a deliberate decision.
  - **Tata's category names are learned in the background (`services/categoryMap.js`), and a query token can be satisfied by the category path.** This is the principled version of the coverage rule below, and it works where that one failed. Tata's search returns only numeric `categoriesIds`; the readable path lives in the product page's JSON-LD BreadcrumbList, one request away — ruinous per product per search, cheap once per unseen id combination. So the search never waits: an unknown combination is queued, a slow background worker (one every 3s, through `fetchWithRetry`) resolves it, and the map persists to `.category-map.json` so it survives restarts. Verified stable: `["191","129","131"]` → `Almacén/Panificados/Pan de Molde`, `["196","116","118"]` → `Frescos/Lácteos/Leches`; ids map positionally to the first N breadcrumb entries, and the trailing entries (product name repeated, then brand) are noise to drop. With that, `tokenSatisfied` admits a product whose *category* contains the token — which separates precisely what text could not: "Pan Lacteado TaTa" sits in `/…/Pan de Molde/` so "molde" is satisfied, "Pan Casero Rebanado" sits in `/Frescos/Panadería/` so it is not, and a Puré de Papas has no "tomate" anywhere in its path. Only El Dorado and Tata carry categories, so for every other store the token is still required in the name — the rule can only add correct results, never leak. Measured: precision held at 99.8%, top-1 99.6%, coverage rose 95.8% → 96.9%, hogar 100%.
  - **Product family comes from the MEF's official catalogue (`services/productType.js`, built by `scripts/build-sipc-types.js`), and it is the one signal here allowed to be a hard filter.** Uruguay's SIPC open data lists 379 basket products with type, brand and package in separate fields, which is exactly the missing "what is this product" that no rule over the name could supply — `Hipoclorito de sodio` against `Agua de mesa sin gas`, `Pulpa de tomate` against `Papa Blanca`, and a literal `Pan de molde lacteado` type that independently confirms the `molde ↔ lacteado` synonymy the miner had found. Classification order is load-bearing and was arrived at by measuring: **an exclusive token outranks the brand** (248 of 272 type tokens belong to exactly one family — `hipoclorito`, `molde`, `pulpa` identify alone, `agua` and `blanco` do not), and the **brand only counts when the product's own name does not contradict it**. Brand-first dropped a real "Agua Mineral Nix Con Gas" because SIPC lists Nix only under gaseosa — it catalogues the Nix cola, not the Nix water. When name and brand disagree the classifier abstains, because a false discard hides a correct product while abstaining just leaves things as they were. `lavandina ↔ hipoclorito` is in SYNONYMS as a dictionary fact (commercial vs chemical name of one substance), not a heuristic. **Why a filter and not a penalty here**: unlike the rules that infer from text, this is positive identification against state data, and it only speaks when both sides are known, so a product outside the official basket is never touched. As a penalty the item merely ranked lower and stayed listed — for "agua 2 litros" that meant bleach among the waters. Result: contamination 0.1% → 0.0%, top-1 99.6% → 100%, supermercado 100%.
  - **Relaxing a query token by corpus coverage was tried, measured and reverted — `requiredTokens` is kept in the code, disabled, so nobody repeats it.** The idea: if one token appears in ~all results the domain is confirmed, so the others become ranking signals rather than gates. It fixes real complaints — Tata answers "pan de molde" with "Pan Lacteado TaTa", "Pan Americano Los Sorchantes" (they sit in Tata's own "Pan de Molde" category) and the word "molde" never appears in the name. But measured over the 260 cases it dropped precision 99.8% → 99.1% and tripled real failures, because it relaxes exactly the token that discriminates: `pure de tomate` (anchor "pure") returned Puré de **Papas**, `tablet samsung` (anchor "samsung") returned an **Aspiradora**, `pava electrica` (anchor "electrica") returned a **Cafetera**. Those have the same shape as the cases it fixes — head plus qualifier — and only the store's taxonomy separates "molde is optional" from "tomate is the product". **Tata exposes only numeric category ids**, so its side of this stays unfixed; widening category capture beyond El Dorado is the real path.

It is restricted to a closed list of Spanish container nouns (`CONTAINER_WORDS`) because the general form is unsafe: unrestricted, it inferred that "tomate" means 520 g and would have passed a "Puré de Papas 520 g" as tomato purée.
  - **Eligibility is "matches the required tokens"; the score only orders.** `_score > 0` used to gate the strict filter, and the main-noun rule's −3 can exceed BM25's whole contribution on a small result set: Tienda Inglesa's Salus scored 0.39 − 3 = −2.61 and was dropped, while the two results that did show came from the typo rescue rather than the main filter. It is now a hard filter with no fallback, which is why "xbox series x" still returns nothing instead of five games and a steering wheel.
  - **The store-search fallback never fires for a token containing digits.** "ibuprofeno" is a generic and the pharmacy knows it sells as Perifar; "ps5" is an exact product code, and when no name contains it there is nothing to infer — Digital Outlet was answering with a "Smart Watch Joyroom". Same rule that already governs model tokens: with digits, exact or nothing.
  - **An accessory word near the end of a name is a spec, not an accessory (`esMencionDeSpec`).** `camara`, `memoria`, `bateria`, `pantalla` and `auriculares` are accessories when they lead the product name and specifications when they trail it. Without the distinction, `isAccessoryFor` flagged "Celular Motorola Edge 70 Fusion 5G 8GB 256GB **Cámara**" as an accessory and the hard filter deleted it — which silently removed **every phone that lists its own specs**, and that is nearly all of them. Reported as "celular motorola returns nothing". The head position (first 3 tokens) still counts as accessory evidence, so "Cámara para Nintendo Switch 2" and "Memoria RAM para Notebook" are unaffected.

Verified against the three cases that killed the text-based rule: Puré de **Papas** is family `papa` while "pure de tomate" asks for `{pulpa, tomate}`; "Celular Samsung" and "Aspiradora Samsung" have no known family at all. Reported as "Tata has Pan Lacteado Bimbo but the cart says it's missing"; with the synonym those listings become *complete* matches and survive the ladder untouched. That gap is honest; inventing the link is the rule-that-looks-right failure this file records twice already.
  - **Applying the full-match ladder PER STORE was tried, measured and reverted.** The cart keeps one product per chain, so it looks obviously right that one store naming a product completely should not speak for the others — and it was diagnosed off a real complaint: the single item in the country containing the literal word "molde" (El Dorado's "Pan De Molde Bimbo Vital Mix De Cereales") made `completos` non-empty and deleted the valid Bimbo bread in five other chains. Per-store took "pan de molde bimbo" from 1 chain to 6. The extra coverage was junk. Use `scripts/diag-cart-misses.js "<term>"` to see, per store, which candidates die and at which step; without it "falta" cannot distinguish "the chain doesn't stock it" from "the matcher discarded it", which are opposite problems.

Junk pairs also survive (`piso → fabuloso`, `liquido → ropa` from "jabón líquido para ropa"), so the lexicon carries risk while delivering nothing on the target. Two signals do cross that boundary: the click log (`search_log`/`search_click`, already collecting, needs traffic) and cross-store entity resolution — Tata's "Pan Blanco Bimbo Cero 500 G" and Disco's "Pan blanco en rodajas BIMBO cero 500 g" are the same product by brand and package, and `groupProducts` already matches exactly that way, so the category could be transferred and the residual word learned.
  - **Static embeddings + hybrid retrieval do not fit this deployment, and the domain-specific substitute is not shippable yet either — `scripts/mine-synonyms.js` holds the measurement.** The plan was BM25 + dense vectors fused with RRF (+7.4% NDCG, 91% vs 65% recall@10 on the WANDS e-commerce benchmark). Checked against the real constraint: the smallest usable multilingual model is 103 MB quantized (`static-similarity-mrl-multilingual-v1`; the Model2Vec multilingual one is 489 MB, and the 29 MB `potion-base-8M` is English-only), while Render's free instance gives **512 MB RAM and 0.1 CPU** — their own docs say "not AI inference". At 0.1 CPU the inference would cost more than the scrape it is meant to avoid.
    - The substitute — mine the synonymy from our own catalogue, using the store category as the context window (PPMI over co-occurrence, cosine between term vectors) — **works on exactly the cases it was built for and fails everywhere else**. From 2,892 products it learned `molde → lactal (0.83), americano (0.71), lacteado (0.46)`, `detergente → lavavajilla`, `refresco → gaseosas`. But it also learned `tata → spaghetti`, `campo → aprox, colita`, `rustico → oslo, rack, puertas` — brand and store artefacts, not meaning — and found nothing for zapatillas, pancho, barbijo, which fall under the frequency floor. A mutual-nearest-neighbour filter removes almost none of it (666 of 681 terms survive). **Do not wire this into matching**: it is the anchor rule all over again — a plausible rule whose harm only shows up when measured. The path that would make it usable is more data, and `search_log` is now collecting it.
  - **Precision is measured, not estimated — `scripts/precision-eval.js` + `scripts/precision-cases.js` (260 labeled cases).** Run it before and after any change to matching/ranking/grouping. Cases assert *properties* (`allMatch`, `noneMatch`, `qty`, `minPrice`, `allHaveUnit`, `expectEmpty`), never a frozen list of expected products — store catalogs change daily and a frozen list rots in a week. Reports precision (over individual results, so a 20-result dirty query outweighs a 2-result one), contamination, top-1 and coverage; exits non-zero on real failures. Cases short on results are reported separately as stock gaps, not relevance errors.
    - **When a case fails, check the assertion before touching the algorithm.** The first honest run of this suite read 84.4% precision, and nearly every failure was a bug in the *test*: regexes written without accents (`/azucar/i` never matches "Azúcar"), and reading `parseQuantity().base` when the function returns `.unit`. Real precision was 99.9%. The harness now de-accents before matching — keep it that way.
    - The accessory guard is synonym-aware (`queryAsksFor`): searching "teclado" must not flag "Magic **Keyboard**" as someone else's accessory. A literal word-by-word comparison did exactly that.
    - Section L covers "sin X" (a product advertising the *absence* of what you searched — "Pulpa de Tomate SIN AZÚCAR" contains the word "azúcar"), and section M is a regression guard with one case per bug already fixed here. Add a case to M whenever you fix a relevance bug; that is what stops it coming back. When re-testing, **run the battery twice on identical code first** — store-side variance alone moves ~18 lines, so a diff smaller than that proves nothing. Zero-result or accessory-only cases (Xbox Series X, Samsung Galaxy S24, iPhone 15 Pro, zapatillas Nike) were each confirmed against the store's own raw search output to be genuine stock gaps — don't assume an empty result is this algorithm's fault without checking the raw scrape.
- **Price history verdict** (`services/priceHistory.js`, built by `scripts/build-price-history.js`): tells the user whether a price is high *for that product*, which is a different question from "which store is cheapest" and one no competitor here answers. The SIPC publishes 13.4M daily prices for 2026 (980 MB); the build script streams it and reduces it to per-product percentiles in a 36 KB file, keeping memory flat with a rounded-price histogram rather than the observations. **Sale prices are excluded from the median** — 1.68M of the 13.4M — because mixing them lowers the "usual" price and makes a normal one look expensive. **The elapsed-time correction comes from the data itself**: the dump covers January–June and was published in July, so comparing today's price against a six-month-old median skews everything toward "expensive"; each product's monthly trend is measured inside the same file and used to project the median forward, instead of importing an external index that would need maintaining. Matching a scraped product to its official record requires **brand, package size and the type's head noun**, then picks the candidate sharing the most type words — requiring every type word fails on real shelf names ("Yerba mate común" in the catalogue is "Yerba Canarias 1 Kg" on the packet), and requiring too little would confuse "Aceite de girasol Óptimo" with the same brand's maize oil. It answers for the 289 basket products with history and stays silent otherwise, because telling someone a price is high by comparing it against a different product is worse than saying nothing.
- **Nearby branches** (`services/nearbyStores.js`, built by `scripts/build-stores.js`): 879 of the SIPC's 893 establishments, all geolocated, across 21 departments — 506 of them belonging to chains we scrape, plus independents that have no online price but do exist and can be found. Turns "Tata is cheapest" into "Tata is cheapest, 600 m away". `masCercanaPorCadena` returns the nearest branch of *each* chain rather than the nearest five overall, which could be five Tatas and would not help anyone decide. Location is an optional query parameter on `/api/shopping/insight`; without it everything else still works and no GPS permission is requested for a secondary feature. **The CSV's header lies**: it declares `long;lat` but column 8 holds latitude and 9 holds longitude. Trusting the header put all 893 branches in the Gulf of Guinea — the Uruguay bounds check in the build script is what caught it, and is worth keeping for that reason.
- **Spending insight** (`services/spendingInsight.js`, `GET /api/shopping/insight`): the one feature a pure price comparator cannot copy. There is a Uruguayan competitor doing the same scraping with 40,000 users and a head start, but it has no access to the user's bank statement — this app does, and the merchant name sits in every transaction description, so it knows both how much the user spends on groceries and **at which chain**. That turns "here are prices" into "you shop at Disco and spend $8,400 a month; your list costs $1,100 less at Tata". Three honest guards, each of which changes the number: the monthly average divides by the months that actually have transactions rather than the requested window (one uploaded statement would otherwise report a third of real spending); spend that cannot be attributed to a known chain is reported separately instead of being assigned; and the comparison only considers stores holding the **complete** list, since a lower total from a store missing two items is not a saving. The monthly projection is explicitly labelled an estimate in the UI, because the list is a sample of the shop, not the shop. Store patterns are keyed to the scraper's own store ids so bank-side detection and price-side comparison cannot drift apart — and deliberately conservative: a short pattern like `ti` for Tienda Inglesa turned "PAGO A TI MISMO" into a supermarket purchase, so unattributed beats misattributed.
- **Search and click logging** (`services/searchLog.js`, tables `search_log` / `search_click`): raw material for Learning to Rank, which is the best-performing ranking method in e-commerce search and learns from what people actually pick. **This history cannot be reconstructed later** — every day without logging is a day of data that never comes back, which is why it exists before anything consumes it. Both halves are stored because either alone is useless: clicks say what was chosen, `shown` says what it was competing against and in what order, and without impressions you cannot correct for position bias (rank 1 is clicked more *because* it is rank 1). `GET /api/prices/search` returns a `searchId` that `POST /api/prices/click` references. The search awaits the log insert — the id has to travel in that response — but **capped at 300ms**: negligible against a request that already spent seconds scraping, and a slow database costs the correlation rather than the user's time. Everything else is fire-and-forget and disables itself on the first error; this is telemetry, never a product feature, and it must never delay or break a search. `limpiar()` at boot drops history older than 180 days.
- **Expo Push**: `services/billNotifier.js` runs a daily cron (09:00 America/Montevideo, via `node-cron`) sending bill-due reminders through Expo's push API. `routes/pushToken.js` registers the device token.

### Frontend structure

`AppNavigator.js` is the single source of truth for screen wiring: a stack (`Login` vs `Main`+`Sugerencias`+`Paywall`, switched on `useAuth().user`) wrapping a custom-drawn floating bottom tab bar (not the default `@react-navigation/bottom-tabs` chrome — see `components/ui/FloatingTabBar.js`). **The 6 tabs and their order do not change** — it is learned navigation. Labels were added in the redesign because an icon-only bar could not distinguish the price search from the shopping list. `AuthContext` owns the JWT lifecycle (`expo-secure-store`, **not** AsyncStorage — keep it that way, this is deliberate for token security) and fires `registerPushToken()` + `initPurchases()` on login/register/resume. `PlanContext` (above) must be inside `NavigationContainer` since some of its consumers navigate to `Paywall`.

**The Movs tab is where movements come IN, and it used to say so nowhere.** The tab is labelled `Movs`, the header said *"Sincronizar"*, and the screen showed **no movements at all** — it is `UploadScreen`. The three ways money enters the app were scattered with nothing relating them: the scanner below the statement box (despite that file's own comment saying *"el escáner va primero"*), the statement box on top, and manual entry on a different tab with nothing pointing there — so for someone who paid cash the app simply had no answer. A currency selector floated loose between them without saying it applies only to the statement file, and the button that **deletes** imported movements was a small grey ghost in the middle that never said how many it would take.
- **It is now ordered by the only hierarchy that matters here: accuracy against effort.** Receipt QR first (exact amount, done at the moment of paying), statement second (a whole month, but you must go and fetch it), by hand last (the only one that can be wrong). The currency selector and the import result now live **inside** the statement card — the selector affects only that file, and the result belongs to that action; it used to render at the very bottom, below two marketing cards.
- **`GET /api/transactions/origenes` turns three buttons into a model.** It returns how many movements came from `ocr` (the bank — the column keeps the old name from when reading a PDF was the only path), `receipt`, and everything else as by-hand, and the screen shows all three **including the zeros**, because a zero teaches too: "by hand: 0" says it is possible. That figure is also what lets the destructive button say *"Borrar los 16 que vinieron del banco"* instead of acting blind.
- **The fear the screen now answers first is "if I upload the same file again, does everything double?"** It does not — the upsert corrects — and nobody knew, so the delete button was the first reaction rather than the last resort. Saying it above the button is what demotes it.
- Copy lives in `src/i18n/es.js`/`en.js` like the rest of the screen (48 keys each, mirrored) — the screen had drifted into hardcoded Spanish for everything added after the redesign.

`src/api/client.js`'s `BASE_URL` is a hardcoded string toggled by commenting/uncommenting between a local LAN IP and the Render production URL — there is no env-based switching. **Check which one is active before assuming why auth/network calls fail in dev.**

**Render's free tier sleeps the service after 15 minutes, and waking it takes 42.5 seconds — measured against production.** The client timeout was 15 s, so the first screen after any idle period failed *every time*, and the failure looked exactly like "no internet". Reported as "me da error de conexión cuando intento iniciar sesión"; the endpoint itself was fine — the same request answered `401 Credenciales incorrectas` in 372 ms once the service was up. Three parts to the fix, and the middle one was the worst bug:
- `despertarServidor()` pings `/health` (no DB, no token) on app start, so the service is coming up while the user is still typing. Fails silently — it is an optimisation, not a dependency.
- **A network error is not an invalid token.** `AuthContext`'s startup effect deleted the stored token on *any* thrown error, so a cold start did not merely fail — it **logged the user out**. It now only clears the token on a real 401 (`esErrorDeRed`).
- One retry with a 75 s budget when no response came back, which is the signature of a waking service. **Only GETs and login/register are retried**: a timeout does not say whether the server processed the request, so repeating an arbitrary POST would create the goal or the deposit twice.
- Raising the timeout alone was rejected: it would leave every genuinely failed request spinning for over a minute. The login toast now also distinguishes the two cases instead of saying "Error de conexión" for both.

### Design system (`src/components/ui/`, `src/theme.js`)

Every screen is built from one component library. Before this existed there were 9 screens, ~10.000 lines with ~2.350 of inline `StyleSheet`, and the same patterns redrawn per screen: **15 primary buttons, 7 inputs, 6 chips, 5 empty states under 3 naming schemes, 4 bottom sheets**, and 66 hex colours against 41 in `theme.js`. Now it is ~460 lines of screen-level style and **zero hex outside `theme.js`**. The design came from a Claude Design handoff kept in `design/` along with the brief that produced it.

**A screen must not define visual style of its own** — no colour, radius, shadow or font-family literals. If something cannot be built from the pieces, extend the piece; drawing it beside them is exactly how the duplication came back last time. Screen-level `StyleSheet` is for layout only (flex, gap, dimensions).

- **The weight goes in the font-family name, never in `fontWeight`.** `@expo-google-fonts/*` exports one family per weight (`Manrope_700Bold`), so `fontFamily: 'Manrope'` + `fontWeight: '700'` is **ignored on Android** and renders regular; iOS sometimes synthesises it, which is worse — right in the simulator, wrong on half of real devices. `TYPE` therefore names a family per style and passes no weight. Use `<Txt variant="…">`, not a bare `<Text>`, so this cannot be sidestepped.
- **Import each font weight by subpath.** `from '@expo-google-fonts/manrope'` pulls the package index, which `require`s every weight — that bundled all 23 faces (2.5 MB) instead of the 7 in use (716 KB). Import `from '@expo-google-fonts/manrope/700Bold'`. `App.js` renders even when the font load *fails*, falling back to the system face: a missing font is ugly, a blocked render is a permanent white screen.
- **Brand palettes carry a separate display value where the real colour is unusable on dark** — `STORE_COLORS[].dot`, `SERVICE_COLORS[].icon`. Measured, not guessed: 5 of 16 chains and 4 of 14 services fail contrast 3.0 (Stadium is black on near-black at **1.08**, PlayStation Plus navy on dark grey at **1.26**). Read them through `storeDot()` / `serviceMeta()`. **A store or service name is never coloured** — only its dot/icon is; 11 of the 16 chain colours don't reach text contrast even when they work as a dot. `CATEGORY_COLORS` + `categoryColor()` follow the same shape, with a name-hash fallback at fixed lightness for user-invented categories.
- **Data colours and feedback colours are separate and must not cross.** `income`/`expense`/`neutralData` are the sign of money; `success`/`warning`/`error` are the state of the system. A red total and a failed request are different things.
- **The optimal cart carries a one-store alternative, and it can be the cheaper one.** A cart that saves $159 by touring four chains is not a plan anyone follows, so the card names the best single store that holds the **complete** list alongside it. Two rules, both found by testing against real data: the comparison only runs when *both* sides cover every item — a single store missing one would look cheap for the wrong reason, the same error `Card variant="partial"` exists to prevent — and **the difference can be negative**, because `optimalTotal` is built from the best value *per unit* rather than the lowest absolute price. When one store beats the multi-store total it is better on both counts and the row says so; hiding a negative would sell the worse option. When no chain has the whole list the row explains that instead, which is what makes the "recorriendo N tiendas" figure above it legible rather than arbitrary.
- **The honesty rules have components, not fine print.** `Badge variant="estimate"` carries "this is a projection", `Card variant="partial"` carries "this store's lower total is missing items, which is not a saving". They are components precisely so the next redesign cannot quietly tidy them away — see the cart rules in the scraper notes above for why each exists.
- `ProgressBar` splits an over-budget bar into the budget and the excess rather than turning solid red, because a bar pinned at 100% cannot distinguish spending the limit from spending double it. `ProgressRing` is `react-native-svg` with an animated `strokeDashoffset` (the handoff specified `conic-gradient`, which RN has no equivalent for).
- **Never show an invented number.** Upload's ring was hardcoded to 72%; a made-up percentage reads as information. It reports the two phases that are actually known.
- **`BottomSheet` pads its bottom with the safe-area inset, and the app has a `SafeAreaProvider` only because of this.** The sheet anchors to the bottom of the *screen*, not of the usable area, so on a phone with a gesture bar its last element sat underneath it. With a primary button this barely showed — a button clipped by 24px still looks tappable — but a sheet with no button clips *content*, and "¿A qué meta va?" was the first one without a button. `react-native-safe-area-context` was already installed (react-navigation pulls it in) and nothing in the app used it; screens hardcode their top padding instead. **`initialMetrics={initialWindowMetrics}` is not optional here**: without it `useSafeAreaInsets()` returns zeros inside a React Native `<Modal>` on Android, which is exactly where the sheet lives.
- **Fluidity comes from WHICH THREAD an animation runs on, not from the numbers.** `useNativeDriver: true` hands the animation to the UI thread, where it does not care what JavaScript is doing; only `transform` and `opacity` qualify. The tab pill was animating `left` **and** `width`, neither of which qualifies, so it ran every frame across the bridge and stuttered whenever the screen was busy. `width` was never needed — the six items are `flex: 1`, so they are all the same width — and the pill now translates natively. Grep for `useNativeDriver: false` before adding an animation: the only legitimate one left is `Progress.js`'s `strokeDashoffset`, which is an SVG prop and genuinely cannot be native.
- **`MOTION` is parameterised the way Apple parameterises springs**, because `friction`/`tension` are numbers nobody can reason about — you cannot look at `tension: 220` and know how long it takes or how much it bounces, so they get tuned by trial. A spring is described by `response` (seconds per oscillation) and `dampingFraction` (1 = no bounce), and the conversion to the physical model RN accepts is exact at mass 1: `ω₀ = 2π/response`, `stiffness = ω₀²`, `damping = 2·fraction·ω₀`. The `resorte()` helper does it, so "make it quicker" is lowering `response` rather than guessing.
- Springs are **interruptible by nature**: retarget one mid-flight and it continues from its current position and velocity instead of restarting. That is most of what reads as continuity, and it is why the tab pill is a spring rather than a timing.
- Screen transitions are already native (`createNativeStackNavigator`). **Dead code warning**: `src/utils/animations.js` is imported by nothing and its helpers animate on the JS thread — do not reach for it.
- **Glass is applied to every control, but `GlassEdge` is what actually unifies them — not transparency.** In iOS 26 a primary button is still the colour of its action; what every control shares is the line of light on its top edge, as though the light source sat above the screen. So `GlassEdge` (exported from `GlassSurface`) goes on *everything*, while the translucent fill goes only where the surface means nothing on its own: `Button` `secondary`, the `Segmented` track, an idle `Chip`, the off state of `Toggle`. **`primary`, `destructive`, `premiumLocked` and `action` stay coloured** — there the colour *is* the information (the same rule that keeps data colours and feedback colours apart), and making them translucent would erase the only hierarchy a screen full of buttons has. `Toggle` follows the same logic: on stays solid, because a translucent "on" would force you to read the knob's position to know the state, which is the one thing a switch has to answer instantly.
  - **The first attempt gave controls a tint instead of glass, and it was invisible — measure the token before trusting it.** `glassFill` at white 7% over the app background computes to `#232221`, against the `#201e1c` of `surfaceRaised` it replaced: three points per channel. Reported as "I see everything the same", correctly — there was no change. The edge had the same problem (`#444240` on `#201e1c`, over 1.5px). `GlassFondo` now puts the **real** material behind every glass control as an absolutely-positioned, `pointerEvents="none"` layer, so the `Pressable` keeps its whole hit area, and the tokens were re-derived from the composited result rather than picked by eye.
  - **The tab bar drags too, with a stricter threshold.** Same displacement technique as `Segmented`, but it demands `|dx| > 6` **and** more than twice the vertical movement, because the bar floats at the bottom edge where the home-indicator swipe lives and an accidental tab change is worse than a missed drag. It navigates only when the index actually changes — otherwise a two-tab drag would fire a navigation on every frame of the gesture.
  - **`Segmented` can be dragged, and the drag is measured by DISPLACEMENT, not position.** Tapping alone makes every change a jump and the pill never follows the finger. Two traps, both deliberately avoided: the `PanResponder` is created once, so reading `ancho`/`value`/`options` from the closure would freeze them at the first render (`ancho` is still 0 there) — it reads from a ref refreshed every render instead. And it uses `gestureState.dx` rather than `locationX`, because `locationX` changes coordinate space the moment the finger crosses onto a child `Pressable`, which makes an absolute reading jump on its own. Starting index plus `round(dx / ancho)` has neither problem. `onMoveShouldSetPanResponder` demands real horizontal movement, so a plain tap still reaches its segment's `Pressable`.
  - **A native view needs `Animated.createAnimatedComponent` before it can take an `Animated.Value`.** Handing `GlassView` a `transform: [{ translateX: <Animated.Value> }]` directly threw *"Transform with key of translateX must be number or a percentage. Passed value: {"translateX":0}"* — the native view receives the object rather than a resolved number. `GlassPieza` wraps it once at module level, and its non-glass fallback is an `Animated.View` for the same reason: a caller passing an animated transform must not care which tier it lands on.
  - **`Segmented`'s selection slides, and on iOS 26 it is a tinted glass piece inside a `GlassContainer`.** It used to just move a background colour from one segment to the next — nothing travelled, so there was nothing to merge and nothing that read as continuity. It now measures the widest segment and gives every segment that width, which is not cosmetic: unequal widths would force the pill to animate `width` and drop off the native thread. With equal widths the pill only translates. **`GlassContainer` was tried here and reverted**: on the device it drew a dark smear stuck to the pill that also covered the neighbouring label. The merging is real, but not with a light pill over a dark track with text underneath it — the pill is a solid colour, which reads. `GlassGrupo` and `GlassPieza` remain in `GlassSurface.js`, unused, so the next person does not rediscover this. The pill passes `interactivo={false}`: it sits behind the labels with `pointerEvents="none"`, so it cannot deform under a finger and claiming otherwise would be a lie in the props.
  - **`isInteractive` only fires if the glass RECEIVES the touch**, which the first version prevented by drawing it as a `pointerEvents="none"` layer behind the content — disabling exactly the behaviour that makes the material feel liquid. `Button` now makes `GlassSurface` the box with the `Pressable` outside it, the same shape the gradient variants already used, so the hit area is untouched and the material sees the contact. **`Chip` and `Toggle` still draw glass as a backing layer**: making it the box there means the native view sits between the finger and the `Pressable`, and whether it claims the touch responder has not been checked on a device — untested and tappable beats clever and possibly dead.
  - On iOS 26 controls use `isInteractive`, which is the genuinely *liquid* part: Apple's material deforms and responds under the finger. Nothing else here imitates that. `expo-glass-effect` declares `"android": {}` — it is Apple-only, so Android never reaches that tier.
  - **`GlassSurface` logs its tier once in dev.** "I don't see the effect" has three possible causes — system material, real blur, or neither — and a screenshot cannot tell them apart from the outside.
  - Anything with a clipped edge needs `overflow: 'hidden'`, which is why `Chip`, `Segmented`'s segments and `Toggle`'s track have it — but **`Button` deliberately does not**, since its `primary` variant carries a shadow and the two fight (see the tab bar note below).
- **Glass refracts what is BEHIND it, so anything opaque back there defeats it.** Compared against WhatsApp's iOS 26 tab bar, ours looked like a panel instead of a pane, and the reason was `GRADIENTS.scrollFade`: a 96px band at the bottom fading to the **fully opaque** app background, with the bar sitting entirely inside it. The material was faithfully refracting a solid dark rectangle. The fade now renders **only when there is no glass** — where it is still needed, since content would otherwise cut off hard — and with glass the material itself does that job. Two more differences from WhatsApp, both removed: **no border** on the glass tier (a drawn outline is what makes it read as a painted panel; in Apple's material the edge comes from the refraction), and `glassEffectStyle="clear"` rather than `"regular"` for the bar, which is what lets content stay readable through it. Controls keep `regular`, because a button has to read as its own surface.
  - **The selection pill is NOT a `GlassView`, and cannot be while it travels.** Apple's material samples what sits behind it in order to refract it, and moving one with a `transform` leaves a trail — reported as a smear appearing in the bar on every tab change. It is a property of the material, not something a parameter fixes. The *look* is reachable without it: white with alpha (`glassPill`) over the bar's glass reads as a denser region of the same pane — which is what WhatsApp's pill actually is — and being an ordinary `View` it translates on the native thread with no artefacts.
  - **`GlassGrupo` and `GlassPieza` are now used by nothing.** Both were tried and both failed on the device: the container drew a dark smear in `Segmented`, the piece smeared when translated here. They stay in the file so the next person reads why before trying again.
- **The floating tab bar is glass (`components/ui/GlassSurface.js`), in three tiers, and only the top one is the real thing.** On **iOS 26+** it is Apple's own `UIGlassEffect` through `expo-glass-effect` — the system material, which refracts, carries specular highlights on its edges and adapts to what scrolls behind it in real time. None of that can be written in JavaScript. Below that (older iOS, **Android 12+** where `RenderEffect` exists) `expo-blur` gives a *real* backdrop blur and the veil and lit edge are painted by hand: it looks similar, it is not the same thing — no refraction, no reaction to content. Under Android 12 it falls back to the opaque surface, because there `expo-blur` only paints a translucent wash and a bright edge on top of that reads as a drawing bug rather than as glass.
  - Both `require`s are wrapped: in Expo Go a missing native module throws at import, and a tab bar that fails to render leaves the app with no navigation. Same pattern as `services/purchases.js`.
  - **The clipping lives on an inner layer, not on the surface.** `overflow: 'hidden'` and a shadow on the same view fight each other — iOS clips the shadow to the border and the floating bar loses exactly what makes it float. The blur clips itself inside; the surface keeps `SHADOWS.ambient`.
  - Glass colours are tokens (`glassTint`, `glassEdge`, `glassBorder`) and carry alpha on purpose: what shows through is the screen. On glass the border also changes from the opaque `border` to `glassBorder`, since an opaque frame around a translucent panel gives the trick away.
- **The main action of a screen is a floating button, because in the header it was invisible.** Adding an income or an expense was a 19px `+` in `COLORS.textMid` inside `ScreenHeader`, sitting between the avatar and the language/logout buttons — the same size and colour as the controls that do nothing important, so it read as a utility icon rather than as the point of the screen. Users reported, verbatim, not understanding what to do on the home screen or how to add a movement. `FloatingAction` now sits bottom-right, above the tab bar, and **the header `+` was removed**: leaving both would dilute which one is the path.
  - **Glass is the material; colour is still the information — that is what resolves "make it glass like the nav bar, but make it stand out".** Glass is quiet by nature and the whole problem was that the control could not be seen. On iOS 26 it is real glass (it refracts and deforms under the finger) but **tinted** with `glassAction`; below that tier there is no material to tint, so it falls back to the solid `primary` fill. Same rule that keeps `primary` and `destructive` coloured instead of translucent.
  - **The tint's opacity was measured, not chosen.** Bone at 72% composites to `#afaca8` over the app background, giving the dark icon **8.34:1**; at 45% it was 3.93:1, which is where an icon starts to disappear. Same discipline as the `glassFill` lesson — the first glass pass was invisible precisely because its token was picked by eye.
  - **It is a bare circle with a `+`** — asked for that way, over the argument that a label removes the interpretation step (the same one that put labels on the tab bar). `FloatingAction` keeps both shapes: with `label` it draws a pill, without one a 60px circle. **Without text, `accessibilityLabel` stops being an extra** — it is the only thing naming the button to a screen reader, which is why `a11yLabel` is its own prop rather than the visible one.
  - It renders **outside** the opacity cross-fade that runs when switching currency: the content may dip to 45% while new figures arrive, but the way to add something must never flicker — least of all on an empty screen, where it is the only place to start. The empty state also **carries the button itself** now rather than describing where it is, and the bottom spacer grew from 110 to 172 so the last block does not hide under it.
- **`ScreenHeader` has a `titleBadge` slot, and the plan mark lives there.** It used to sit in the row of utility buttons with a flexible spacer pushing it to the far end, which put a *status* label among things you tap. Premium is now just the diamond glyph in `COLORS.premium` beside the name — no pill, no gradient — because next to a name a gold pill wins the look away from the name itself; it reads like a verification tick, findable if you look for it and quiet if you don't. **Free stays a pill**, small and muted, because there the mark genuinely does invite a tap (it opens the paywall). The title shrinks before the badge does, so a long name truncates instead of dropping the mark.
- `Toggle` is used instead of RN's `Switch`, which paints itself with per-platform system colours and breaks the palette.
- Icons: `import Ionicons from '@expo/vector-icons/Ionicons'`, never the package root. **Known and unresolved**: all 20 icon fonts (4 MB) are still bundled anyway. `assetBundlePatterns` was tested as the cause and ruled out; the real cause is unidentified. Pre-existing, not worth guessing at.

- **Claims in the copy have to match what the code does — this has now been wrong twice.** First the app promised end-to-end encryption it does not have. Then the Upload screen said it analyses your statements "con IA avanzada" and labels them into "24 categorías". There is **no AI anywhere in the upload path**: `ocrParser.js` is regexes and a CSV reader, `categorizer.js` is 15 regex rules, and anything unmatched lands in `Otros`. There are 16 categories, not 24. The only real model call in the product is `routes/suggestions.js` (Claude Haiku, premium), and the five strings describing *that* are accurate — those stay. The rest were rewritten to say what happens, including the part worth setting expectations about: what the categoriser does not recognise ends up in Otros and the user can change it. **When a feature changes, grep `src/i18n/` before shipping**; false copy about money and security is worse than none, and a paywall bullet that oversells is worse still.
- **`SecuritySheet` tells the trip, and never argues about a term.** Reachable from the Dashboard header and from Upload's privacy card, which is where someone handing over a bank statement actually wonders. Two things were wrong before and both are worth not repeating:
    - **The app claimed end-to-end encryption in two i18n strings and it was false** — `featurePrivateDesc` on the upload card, and `featureUpload`, a bullet **selling the premium subscription**. The server decrypts the file to read it. A false security claim is bad anywhere and worse in a paywall.
    - **The first version of the sheet asserted and then retracted** ("it's encrypted… but it isn't end-to-end"). Reported as confusing and as *feeling less safe*, which was right: claim-then-walk-back breeds doubt even when the underlying system is sound. The mistake was debating a piece of jargon instead of describing what happens.
  - It now opens by answering the question directly — *nobody in transit; MoneyFlow yes, for a few seconds* — because those are **two different threats** and the reader should not have to separate them alone. The service being able to read it is not a weakness: without decrypting there are no categories, no detected subscriptions, no price comparison. Told as an ordered trip (phone → wire → server → what remains), the honest part is a step rather than fine print. If any step stops being true, this sheet is the first thing to change: a security explanation that has drifted is worse than none.

**Nothing here has run on a device** — every screen is compile-verified (`npx expo export` on both platforms) and nothing more.

## Security posture (as of the last audit/fix pass)

- JWT: HS256, symmetric secret (`JWT_SECRET`), 7-day expiry by default. `jsonwebtoken`'s default `verify()` restricts accepted algorithms to HS* when given a plain string secret, so no `alg:none`/algorithm-confusion risk.
- `POST /api/webhooks/revenuecat` **fails closed**: returns `503` if `REVENUECAT_WEBHOOK_SECRET` isn't set (never silently accepts unauthenticated requests), `401` via timing-safe comparison on mismatch. This must be set in **every** environment (local `.env`, Render, and Railway if that's ever fixed) — there is no "it's fine in dev" exemption baked into the code.
- `routes/dev.js` (simulate-premium/simulate-free) mounts only when `NODE_ENV === 'development'` (allowlist, not `!== 'production'` blocklist) — deliberately fails safe if the env var is ever missing/misspelled in a real deployment.
- CORS is an explicit origin allowlist (`ALLOWED_ORIGINS` env, comma-separated). Requests with no `Origin` header (native app, curl, server-to-server webhooks) always pass — this is a mobile app authenticated via Bearer token, not cookies, so CORS isn't a CSRF boundary here, just a hardening measure against browser-based abuse of public endpoints.
- Upload encryption: see "Upload pipeline" above — real hybrid RSA+AES, not theater.
- Body size limit: 15mb (was 50mb — lowered as a DoS-surface reduction; if a legitimate use case needs bigger payloads, raise deliberately, don't just revert).
- **`.claude/` is gitignored — never commit real credentials inside it.** `settings.local.json` previously leaked real MercadoLibre `client_id`/`client_secret`/access-token values for ~4.5 months in this public repo, because they'd been pasted into ad-hoc `curl` commands that got captured as permission-allowlist entries. Rotated at the source and purged from git history via `git-filter-repo`. If a command you're about to run contains a real secret, don't run it as a one-off shell command that the permission system will remember verbatim — read it from `.env` inside a script instead.
- **Bank statements are gitignored by EXTENSION** (`*.csv`, `*.pdf`, `*.xls`, `*.xlsx`, `*.ofx`, `*.qif`), not by filename: the next statement a user drops in the repo root will be called something else and nobody will remember to add it — which is precisely how `settings.local.json` sat in a public repo with real credentials for four and a half months. No `.csv` or `.pdf` is versioned today, so this hides nothing legitimate; `git add -f` forces one through, and that friction is the point.
- Known finding, now **partly resolved by evidence**: `services/ocrParser.js` depends on `pdf-parse@1.1.4`, which bundles a pdf.js from ~2016 and fails ("bad XRef entry" / "Invalid PDF structure") on PDFs from some modern generators (confirmed with a hand-built minimal PDF and `pdfkit` output). **A real Santander statement does NOT trigger it** — the library extracted 2,334 characters cleanly. The failure there is one layer up: the text arrives tabulated at ~13 characters per line and `parseSantanderFormat` matches nothing, so the PDF yields 0 transactions while the same statement as CSV yields 16. When a user reports a failed upload, that is the distinction to check first — library error versus parser mismatch are different bugs with different fixes, and the CSV path sidesteps both.

## Deployment

- **Render** (`https://money-flow-co41.onrender.com`) is the real, live production backend. Root Directory = `backend`, Build Command = `npm install`, Start Command from `package.json`'s `start` script. Required env vars: `DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `NODE_ENV=production`, `REVENUECAT_WEBHOOK_SECRET`, `UPLOAD_RSA_PRIVATE_KEY_B64`, `ANTHROPIC_API_KEY`, `MERCADOLIBRE_SITE`, `ALLOWED_ORIGINS` (optional). Auto-deploys on push to `main`.
- **Railway** (project "satisfied-encouragement") is also connected to this repo's `main` branch but has had **every single build fail for 4+ months** — it was never configured with a Root Directory, so its build system (Railpack) scans the monorepo root, finds no recognizable app, and aborts before even reaching `npm install`. As of the last check it's unused/abandoned; don't assume it serves anything. If it's ever revived, it needs the same Root Directory (`backend`) + env vars as Render.
- The DB (Supabase free tier) auto-pauses after inactivity — a `db/index.js` connection error like `(ENOTFOUND) tenant/user ... not found` with DNS resolving fine usually means the project is paused (resume it from the Supabase dashboard) or the pooler host/region in `DATABASE_URL` is stale (re-copy it from Supabase → Project Settings → Database → Connection Pooling).
